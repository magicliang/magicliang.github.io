深入压测（00）容量需要什么证据

Created2026-11-22|Updated2026-11-23|工程实践
|Word Count:1.4k|Reading Time:4mins|Post Views:

压测端每秒启动 1,000 次会话，订单接口返回了 24,000 个 HTTP 202，消费者却还有几千条消息没处理。要验收一次大促，三个数字里只有第一个描述输入，第二个描述同步受理，第三个暴露了尚未结清的后台工作。用户能否在承诺时间里拿到订单结果，要把三处记录按同一批订单对起来。

一条容量结论需要同时说明负载形状、系统边界、业务完成条件和观察时间。任何一个条件改变，结论都需要重新解释。

从一次购物会话开始

以下是贯穿本系列的虚构交易系统。每秒发起 1,000 次购物会话，其中约 80 次最终提交订单。一次订单受理后写入订单状态和待发送事件，后台将事件送入消息队列，消费者确认库存并更新可以查询的订单状态。业务约定 99.5% 的逻辑订单在 2 秒内得到正确终态，这就是例子中的服务等级目标（SLO）。实验数字只用于说明计算。

位置 计数单位 可以证明的事实
压测机 启动的会话 / 秒 调度器实际启动了多少脚本迭代
网关 HTTP 请求 / 秒 路由收到多少次请求，包括重试
订单服务 不重复的逻辑订单 / 秒 多少订单被受理并进入处理链
消费端与结果库 在期限内正确完成的逻辑订单 / 秒 用户能按期限取得多少正确结果

一笔订单超时后可能被重发两次，网关看到三次请求，订单表应只有一笔逻辑订单。压测报告若把请求数当订单数，重复调用就会被记作增产。即使重试实现正确，三次请求仍然占用三次入口资源，到了扩容测算时又得把它们算回来。

---
title: 交易压测的输入与验收边界
---
flowchart LR
    L[会话发压] --> G[网关接收请求]
    G --> O[订单受理与保存事件]
    O --> Q[消息队列]
    Q --> E[库存与订单终态]
    E --> V[校验按时完成与业务结果]

全链路的结束位置由承诺决定。如果承诺是「订单已进入处理队列」，可以在可持久化的受理点验收，同时单独声明下游处理目标。若承诺是「订单已确认」，202 只能作为中间观测点。这条界线也决定后文哪些组件必须保留，哪些可以由测试替身承接。

一组压测可以回答哪些问题

问题 适合的试验 交付物
换索引后单条语句有没有变快 固定数据与并发的组件基准 同输入下的延迟、吞吐和资源对比
新版结算能否承接活动预测 代表性业务混合负载，完整完成边界 目标负载下的 SLO、队列状态和业务对账
突发或丢失一个可用区会怎样 保留流控的脉冲与受控故障试验 拒绝行为、业务影响及恢复时间
长时间运行会不会持续退化 覆盖缓存、GC、维护与积压周期的耐久试验 随时间变化的耗时、内存、延迟与积压走势
如何做性能测试的问题下的答案 按组件基准和黑盒 API 测试区分了观测范围。如何做全链路压测 记下了大促实践中的业务漏斗、基础数据、影子区、预跑和复盘。压力测试需要关注的注意事项 补充了 MQ、缓存、搜索及标记丢失的排查点。把两篇笔记放进同一条链路，可以先用漏斗预测流量，再通过边界对账判断压力是否真的走完。AWS 也将组件级试验和代表性全系统负载视为不同层次的证据。[AWS Well-Architected 指南](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel07-bp04.html)

评审「能否承受 1,000 会话/秒」之前，可以先画出容量结论覆盖的第一条路径。从会话启动画到最终业务状态，在每条边上写上计数单位，标出哪里发生重试、批处理或结果查询。图上若没有终态的观测点，后续再精细的 HTTP 曲线也只能回答到受理为止。
