深入压测（02）从业务漏斗推导负载

Created2026-11-22|Updated2026-11-22|工程实践
|Word Count:1.5k|Reading Time:4mins|Post Views:

活动预测给出每秒 1,000 次购物会话，网关、订单库和消息队列却各有自己的计量单位。给三个系统都填 1,000 QPS，会让订单写入过重，也可能把热门商品上的库存锁争用压轻。负载模型是从业务入口推导每层工作量的过程。

把业务漏斗换成请求速率

以下数字沿用系列的虚构交易。比例是以上层 1,000 次会话为同一基数的简化统计，表中的校验和提交仍存在真实前置状态。

动作 假设 估算量级
商品浏览 每次会话平均 3 次 3,000 HTTP 请求/秒
搜索 30% 的会话搜索一次 300 HTTP 请求/秒
结算校验 12% 的会话校验一次 120 HTTP 请求/秒
提交订单 8% 的会话提交一笔 80 个逻辑请求/秒
重试下单 原始订单请求中 10% 额外尝试一次 88 次提交尝试/秒，包含首次请求

若每笔新订单平均涉及两个 SKU，且每个 SKU 独立执行一次库存处理，每秒受理 80 笔时，平均对应 160 次初次 SKU 处理/秒。这里假定订单去重发生在库存请求之前。若重试也进入库存层，或者一次批量库存 API 合并两个 SKU，调用数和资源成本都要改算。容量模型应在链路图上写出幂等位置、扇出、批合并和失败后的重试次数。

抽样统计先对齐时间窗。秒杀开场的一秒峰值不能由五分钟平均等量替代。按常态、活动峰值和恢复分别计算动作混合，给上游促销节奏变化留一组单独的情景。举例说，库存热点突然从前 100 个商品集中到 3 个，即使全站 RPS 相同，单分片请求和行锁竞争也会改变。

用会话保住因果，用接口补足独立负载

下单脚本需要先取得有效商品、购物车版本和合成账号身份。每笔新业务使用独立幂等键，重试时复用原键。若反复提交同一个业务键，测到的主要是去重查询。若每次重试重新造键，测试会错误增加订单数。

一种可行的混合模型是给整个购物会话设置独立到达计划，把浏览、校验、提交与结果查询留在会话内部按业务顺序执行。对来自合作方、独立调度任务或定时回调的请求再单独建输入场景。会话本身是开环到达，内部依然等待前一个动作完成；故障时后续 API 的 RPS 会按业务进度改变，报告应同时看会话与 API 两层数据。Schroeder 等，NSDI 2006

输入来源 保留的信息 需要补齐的内容
构造脚本 可复现的业务顺序、状态和断言 真实参数分布、突发及罕见分支
脱敏日志回放 参数形态、流量混合与部分时间关系 过期令牌、动态 ID、响应依赖和原始系统边界
实时镜像 此刻已有流量的组合 高于现有峰值的负载和独立的业务结果验证

回放原始请求时，应在目标环境重新建立身份、对象和会话关系，按用户或业务键保留必要顺序。采样率要记录，敏感载荷需筛掉或脱敏。提速回放以前，先确认调度不会打乱前置依赖。镜像是复制已有流量，例如 Istio 默认丢弃镜像响应，镜像侧有无正确完成仍需独立观测。Istio 流量镜像文档

数据规模与数据分布同时属于负载

一张只装几千条记录的订单表，即使请求比例正确，索引工作集、缓存命中率与实际业务也可能相差很远。数据准备记录应包括表和索引的规模、活跃工作集、热点键比例、读写路径、记录年龄、载荷大小及可见状态。冷热两个阶段分别跑，冷态看依赖承压与恢复，热态看活动计划假定的缓存命中能否被维持。

旧文用历史活动和新增场景组装业务模型，再从线上基础数据中采样、过滤、脱敏。这个方法可以直接移植到合成数据：用历史分布控制合成账号和 SKU，新增玩法用明确假设补足。每个假设都能反馈到表格里的一个数，比如热点转移、校验次数或支付回调时延。如何做全链路压测

发压前做一次小样对账

先启动少量能人工核对的会话。观测每个业务分支的次数、参数差异、成功率、缓存命中与消息结果。会话转化有随机波动，应在足够大的样本上和模型比较。用固定样本集验证确定性分支和幂等，再在接近峰值时检查热点和到达形状。预跑中的业务断言若只要看见某个 HTTP 状态码就通过，应补一个跨越最终状态的断言。

最终把脚本版本、数据种子、比例来源、到达调度和验证口径写进同一份运行配置。下次回归用同一版本比性能，真正的业务变化则另建一版负载模型。
