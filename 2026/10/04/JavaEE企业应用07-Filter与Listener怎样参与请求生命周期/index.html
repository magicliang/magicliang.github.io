Java EE 企业应用 07：Filter 与 Listener 怎样参与请求生命周期

Created2026-10-04|Updated2026-10-10|技术
|Word Count:4k|Reading Time:12mins|Post Views:

请求 ID 写上去了，为什么还可能丢失清理

采购申请查询进入 Web 应用之前，希望给每次调用分配一个请求 ID；无论后续成功、业务异常还是内部派发，都不应把本次的跟踪数据带进下一个请求。常见实现是在过滤器中设置 ID，然后调用 chain.doFilter()，最后移除。这里有两个容易混同的“之后”：调用链返回过滤器的时刻，与响应已写完且所有异步任务都结束的时刻。同步请求通常可以以 finally 清理本线程工作；异步请求的真正完成时点则需要额外机制。

本篇源码、迁移、脚本与测试可从固定版本完整归档取得；版本 20261005-local（基于 1b08ada），SHA-256 见源码清单。

现有工程已有 RequestIdFilter.java 和 StartupListener.java。前者覆盖 /servlet/*、/api/* 的 REQUEST、FORWARD、ASYNC 派发，后者在上下文初始化时保存启动时刻并在销毁时移除；源码存在不等于异常/异步派发已实际演练，也不等于这个请求 ID 可在服务器重启后恢复。

过滤的是一次派发，不一定是一次客户端请求

Jakarta Servlet 6.1 §6 描述过滤器生命周期和过滤链：容器在处理映射匹配的派发时调用过滤器，过滤器可以先检查请求、包裹请求/响应，再决定是否执行下游链。chain.doFilter(request, response) 才把控制权交给下一个过滤器或目标 Servlet；如果拒绝访问而不调用它，目标不会凭空执行。过滤器完成初始化后可能被多个线程同时调用，因此把 requestId 存在实例字段同样会串值。当前实现使用局部 String requestId 和请求属性，不用共享字段，且把响应头 X-Request-ID 写在交给下游之前。这个值由服务器生成，不是把客户端自报的头无条件当成可信跟踪 ID。

@WebFilter 显式列出 DispatcherType.REQUEST、FORWARD、ASYNC，没有列 INCLUDE、ERROR。因此一个 HTTP 请求若发生一次匹配的 FORWARD，过滤器可能再次运行并生成另一个 ID；不能把“每个浏览器请求正好运行一次”当成规范要求。内部错误页用 ERROR 派发时此过滤器不会因为 /api/* 匹配就自动覆盖该类型。反过来，有些失败没有派发错误页，容器直接结束异常请求；即使把 ERROR 加到列表，不能由此断言每个异常都会执行两次。实验要分开记录入口派发类型、目标路径、是否真的发生第二次过滤、每次分配的值以及客户端最后看到的响应头。

这也暴露现有实现的一处边界：每次派发都新建 UUID，随后设置并最终移除同一个 requestId 属性。若 FORWARD 在原过滤器调用栈内再次经过过滤器，内部 finally 会移除属性，外层之后可能再也找不到原值；客户端响应头的最终取值同样受写入顺序和响应提交时间影响。要让一次外部请求及所有内部派发共享稳定关联值，需要在入口第一次生成、后续派发复用，并确定在真正生命周期结束时清理；若业务需要区分子派发，另记录派发序号，不要复用一个字段表达两种含义。当前代码没有实现此策略，不能宣称已经保证“跨所有派发同一 ID”。

拦截范围有两个维度：路径与派发类型。/api/health 命中 /api/*，/approval.xhtml 则不在现有两个 URL pattern 中；即使页面调用了同一个采购用例，也不意味着这段过滤器在所有入口都写过响应头。FORWARD 到另一个匹配路径时，要记录目标映射与实际派发类型；INCLUDE 则使用另一类型。想统一采购请求的追踪 ID，必须先清点 Servlet、REST、Faces 各入口，再确定是整笔外部请求共用一个 ID，还是每次内部派发都有子 ID，不能因为某条日志里有 UUID 就算完成全站关联。

finally 能处理异常，但不是异步完成监听器

过滤器当前的同步清理结构是 try { chain.doFilter(...) } finally { request.removeAttribute("requestId"); }。如果目标 Servlet 抛出异常且堆栈退回过滤器，finally 确实执行；这只保证当前调用栈上的属性移除，不保证容器一定能返回某个固定状态，也不保证清理已关闭业务连接。错误如果在响应部分写出后发生，可能已无法修改状态码；捕获异常、记日志和决定是否继续派发错误页应由明确的错误处理契约控制，不能在过滤器里把任意异常吞掉然后返回 200。

异步路径更复杂。Servlet 6.1 的异步处理允许调用开始异步后先退出原调度线程，后续再派发或完成响应。仅在 dispatcherTypes 中列 ASYNC 不会启用异步支持：当前 @WebFilter 未设置 asyncSupported=true，默认不支持在经过它的 REQUEST 链中直接启动异步；异步实验须在隔离工程中检查并配置整条链涉及的过滤器及 Servlet 的异步支持，再新增入口。原 finally 的执行点可能早于异步写出；如果要在响应真正完成、超时或错误时清理与异步工作相关的资源，应对持有的异步上下文登记完成/超时/错误回调，并保证所有退出路径释放一次。不能把 JDBC Connection、线程局部变量或请求属性随意塞进异步任务并假设仍在原线程；使用了容器管理资源也应明确异步任务的受管边界。当前过滤器仅移除普通请求属性，并未持有连接或注册 AsyncListener，故“异步资源释放”实验 NOT_RUN，也没有可误报为通过的连接池对照。

RequestIdFilter 中将 ServletResponse 强转为 HttpServletResponse 是因为本例运行在 HTTP Web 入口；如果在一般 Servlet 协议入口复用同一类，应先检查类型。下游若在过滤器设置头之前完成提交，就不能再补头；本例先设置再交出控制权，减少这一风险，却没有覆盖代理篡改响应头或写后回滚失败。对日志关联，应使用明确的请求范围字段并在错误日志中打印一次被批准的关联值，而不是把申请数据或凭证放进 UUID；一条 HTTP 头也不能代替事务与数据库审计记录。

另一个常被误认为已清理的对象是 ThreadLocal。当前过滤器没有 ThreadLocal，因此不存在它的清理证明。若未来把租户或请求 ID 存入线程局部变量，同步 finally 只能清理当前调用线程上的值；容器线程复用时漏清理会污染下一请求，而异步回调不能假设在同一线程。要验证这种风险，须在异常请求后让工作线程处理另一租户的请求，采集服务端观察到的身份及请求关联；没有可控调度和探针就保持 NOT_RUN。请求属性、ServletContext 属性和线程局部值是三个不同作用域，相同键名不能让它们共享生命周期。

Listener 关注的是容器事件，不是业务状态

Servlet 6.1 §11 规定 ServletContext 及会话、属性等多类监听事件。现有 @WebListener 实现 ServletContextListener，contextInitialized 将 Instant.now() 记在 Web 应用上下文的 startupTime 属性，contextDestroyed 移除它。此属性在同一部署的应用范围内可见，不应被当作每笔审批的创建时间。重启后重新计算启动时刻是合乎设计的；若需要跨进程保留采购审批进度和幂等请求，应写数据库而非 servlet context 或内存集合。销毁回调能协助释放应用级资源，但异常终止进程或强制杀掉容器时不保证执行完整；业务正确性不能依赖它代替提交或恢复。

验收启动监听器须识别部署实例：启动后由受控探针读到 startupTime；正常停止时观察销毁回调；重新启动应得到新实例时刻。当前工程没有暴露该属性的探针，也没有保存 Listener 回调日志；从 /api/health 返回 ready 无法推出上下文属性何时创建、销毁后是否可见。即便日志中有服务器启动信息，那也是服务器/应用部署观察，不是 Listener 属性读写的直接断言。若以后添加 HttpSessionListener，其会话计数与真正在线用户数亦不能画等号，失效、重启与多实例路由都会改变观测口径。

Listener 的启动失败与普通请求失败还不能混为一谈。若上下文初始化时试图打开数据库连接并抛出异常，应用可能无法部署成功；现有 Listener 只设置 Instant，并没有做连接初始化，因而 /api/db-check 的一次成功不能归到它的功劳。容器关闭时依赖监听器“自动清掉每笔申请状态”也会丢掉未完成请求的恢复线索。长期资源如果确实由 Listener 创建，就要在正常部署、热更新、初始化中途失败、强制终止四个分支记录创建数和释放数；强杀场景不能指望收到 contextDestroyed，需用外部资源的 TTL/重连或显式恢复协议兜底。现有 startupTime 是观察部署生命周期的最小例子，不承担订单或 Session 的恢复。

拒绝型过滤器也须给出清楚的负例：如果未来在 Filter 中做认证检查，未授权时应结束链并确认目标服务/数据库没有发生写入；在链之后执行拒绝检查则太迟。当前 RequestIdFilter 不是认证过滤器，不检查角色与租户，把它拿来判定采购申请能否批准会越权推断。实验与代码差距另见 07实验说明。

对异步完成的验收不能只写“finally 曾执行”。受控目标 A 在 REQUEST 中 startAsync() 后返回，目标 B 在后续 ASYNC 派发中完成，目标 C 在超时与错误事件上分别记录一次完成；同一个外部请求的两次派发是否复用 ID，要和过滤器的调用次数分开计数。比较响应头时注意第一个阶段可能已经提交了头，第二阶段再调用 setHeader 不一定改变客户端所见；比较请求属性时还需确认异步上下文是否保留请求对象及何时清理。只有把请求号、派发类型、线程名、事件与最终头关联起来，才能知道 ID 在哪个阶段丢失。当前应用没有 A/B/C 测试目标，此处是清晰的待实现时间线，而不是对 Open Liberty 的运行报告。

两道练习与答案

练习一： 一次外部 REQUEST 派发到 /api/a，目标把请求 FORWARD 到 /api/b；两个路径都命中过滤器。按当前代码，在二次派发中各生成什么，为什么最终响应头不一定对应最初的值？如果希望全程同一个请求 ID，应调整哪里？

答： 两次进入 Filter 都会各生成 UUID，内部派发还会覆盖请求属性和响应头；原请求的 finally 清理发生在其调用栈结束时。响应提交时实际最后写入的头值不能由外层生成顺序一概保证。入口先检查是否已有请求 ID，后续派发复用已验证的请求范围值，并定义在整个请求真正结束时清理；若要给子派发独立编号，另用字段。通过记录两次派发类型、属性值、头值与调用顺序做断言，当前工程尚无此测试。

练习二： Servlet 调用异步开始后返回，过滤器 finally 移除请求属性；异步任务在另一线程稍后抛错。能否根据 finally 执行宣称数据库连接和响应都完成了清理？应记录哪三个结束事件？

答： 不能。原调用栈退出与异步任务完成不是同一时刻，过滤器甚至没有持有数据库连接。异步逻辑需要完成、超时和错误三类回调的清理判据；在每种路径核对一次且仅一次释放、响应状态与可写性、请求 ID 是否仍可追踪，再用独立连接检查数据库终态。该实验需要新增异步目标及监听器，现有源码并未提供，保持 NOT_RUN。

一个请求 ID 的价值还要在跨层日志里验证：Servlet 入口、业务用例和 SQL 操作应记录同一可追踪标识，同时把租户、申请号等敏感字段限制在授权的日志域。当前 Filter 只写请求属性与响应头，没有给用例注入该值，也没有规定异常处理器如何记录；因此即使脚本断言 HTTP 头存在，依旧无法通过这枚 ID 检索一笔审批的完整链路。若要把请求 ID 传入异步任务或消息，必须显式携带并在接收侧确认来源与边界；把 Java 线程局部变量复制到后台线程既脆弱，也不能提供持久化恢复。该项跨层日志合同尚未实现。

限制与官方资料

Filter 链、Listener 回调是 Web 入口机制，不等于请求认证、业务事务或跨节点状态一致性。本章不把拟议代码冒充已部署能力，也不把 finally 解释为异步完成通知。GitLab master 链接是本地源码对应的预期发布路径，工程仍有未推送文件，发布时须重新验证远端实际字节。
