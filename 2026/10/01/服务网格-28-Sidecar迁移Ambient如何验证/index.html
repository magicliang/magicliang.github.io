服务网格 28：Sidecar 迁移 Ambient 如何验证与回退

Created2026-10-01|Updated2026-10-10|技术
|Word Count:2.2k|Reading Time:7mins|Post Views:

给 namespace 换标签，为什么不足以宣布迁移完成

第 04 篇描述随业务 Pod 部署的代理，第 26 篇将四层移到 ztunnel，第 27 篇讨论七层 waypoint。三者覆盖点不同：**标签声明意图，Pod 是否仍有 sidecar、流量经哪个代理及安全策略在哪里执行，必须分别取证。**对于已有 sidecar 的 Pod，仅改 namespace 标签不能让其就地消失；混合阶段须按冻结的 Istio 版本核验代理优先级、滚动重建和路由结果。

迁移不是换一个部署模式名称，而是给每个已有能力重新确定执行位置。以累计应用为例，orders → inventory 的身份与四层保护可以通过 ztunnel 重新验收；请求头灰度到 v2、对 POST /reserve 的方法级拒绝要核对 waypoint 的附着及七层策略。sidecar 的 VirtualService/DestinationRule subset 不能原样假定可作为 ambient 中 HTTPRoute 的版本后端；要按目标发布版支持范围，用实际可用的 v1/v2 Service 和 endpoint 验证。请求返回正确库存版本是必要证据，不是足够证据：仍可能绕过授权点。

先盘点能力，再转换策略

迁移前的观察 ambient 目标执行点 必须重跑的反例
sidecar 对等身份与传输保护 ztunnel L4 与 HBONE 相关连接段 错误 ServiceAccount、未入网格来源
以请求头分流 v1/v2 已绑定 waypoint 的 HTTPRoute 错误头、空后端、直达 Pod IP

表中 L4 身份和 L7 来源不可以替换着读：当请求经过 waypoint 时，目标 ztunnel 看到的对等身份可能是 waypoint；sidecar 来源与网格外来源是否走 waypoint 又取决于实际拓扑。若过早把目标端四层策略收紧为“只许 waypoint”，未迁移的合法 sidecar 调用可能被拒绝；若为避免误拒而把策略全放开，旁路却可能绕过七层拒绝。顺序应该是先确认每种来源的实际路径，再在隔离流量中验证强制约束。

回退同样要求真实请求验收：恢复前一版本的选择标签与策略、按批准的批次重建 Pod，检查 sidecar 确实回来、旧长连接处理方式符合预期，再重跑正反用例。只“kubectl 回写标签”不保证已有连接重选路径；只看到健康检查 200 也不能替代七层拒绝恢复。任何故障只对隔离合成服务注入，先保存快照再回滚，不清理其他环境。

尚未建立 sidecar/ambient 混合集群，全套迁移、回退、旁路和新旧连接对照均 NOT_RUN。本机进程成功和文章中的矩阵是待执行的验收设计，不是已迁移结果。

迁移整组调用链，而不只重建库存

mainline/28/switch.sh 在本系列专用 namespace 中切换五个 Deployment：frontend、orders、inventory-v1/v2、external-stub，并重建 mesh-probe 与 wrong-probe。namespace 标签影响其中全部工作负载，不能移除 ambient 纳管后只为库存注入 sidecar，否则原 ambient 调用方失去身份，无法访问 STRICT 库存。此脚本要求该 namespace 只有这组实验应用与本章 waypoint；其他业务应使用各自独立的迁移批次。

sidecar 分支取消库存 waypoint 绑定、移除 namespace 的 ambient 标签并开启注入。它保留 STRICT，应用 sidecar-l7.yaml 允许 orders 的 GET /quote，删除更宽的 L4 ALLOW，并用第 34 篇 VirtualService/DestinationRule 提供 v1/v2 header 路由。随后重建全部五个 Deployment 和两个探针；验收须确认调用方和目标均含 istio-proxy、证书身份正确，再发送正负请求。标签或 rollout 成功不能代替这些检查。

bind 先为目标安装允许 orders 与 waypoint 两种来源身份的过渡 L4 策略，再设置 Service 绑定。先重跑第 27 篇的 v1/v2、POST 拒绝请求，确认 L7 行为与 waypoint 活动配置；此时直连尚未封闭。通过后运行 enforce，仅保留 waypoint 到库存的 L4 允许项，再测试 Pod IP 绕行被拒绝。

脚本按维护窗口执行，不承诺零中断或策略跨对象原子更新。短暂混合阶段不作功能完成判定；特别是旧 sidecar 来源不能仅凭目的 Service 标签就被假设经过 waypoint。生产灰度需要按独立 namespace/明确标签批次设计共存，本例不把整组重建称为不停机灰度。

故障注入选择取消 Service 的 waypoint 绑定；启用 waypoint-only 后，允许身份的正例也应被拒绝。恢复绑定需重新经过过渡策略、正例验证和 enforce，最终重新验证直连被拒。回退到 sidecar 时同样暂停实验输入，执行整组重建，不只重建库存：

练习与参考解答

  1. 入网标签已变更，如何证伪“所有工作负载已经无 sidecar”？参考解答：列出变更前后的真实 Pod 容器及创建时间、代理资源和 ztunnel/waypoint 请求日志；保留尚未重建的旧 Pod 作为反例，再分别测服务调用。标签不能替旧 Pod 卸载代理，也不说明请求已改走 ambient。
  2. 迁移后 canary v2 成功、正常 GET 200，但旁路 POST /reserve 也可写入，应判定迁移成功吗？参考解答：不能。安全门禁失败，账本显示预期拒绝点未生效；定位来源路径与 Service/Pod IP 附着，核对目标 ztunnel 对 waypoint 身份的四层限制，在隔离环境修正后重测合法请求与旁路负例，不通过就回退。

官方参考与系列导航

  • Enable ambient mode 与 waypoint：分批变更与目标附着；实际命令必须按冻结版核对。
  • Kubernetes Deployment rolling updates：重建与回退对已有 Pod 的影响；不替代网格路径验证。
