如何画和理解轨道图：以 Elasticsearch Query DSL 为例

Created2026-10-10|Updated2026-10-21|技术
|Word Count:8.2k|Reading Time:28mins|Post Views:

《查询与检索》里有一张像铁路线路的图：从 start 出发，经过分叉和回路（loop），最后抵达 end。它不是 Elasticsearch 的执行流程图，也不是网络拓扑图，而是一张轨道语法图（railroad diagram）。

轨道图只回答一个问题：一段结构化输入有哪些合法的排列方式？

以 Query DSL 为例，图中可以同时表达请求体的顶层参数、query 的值以及 bool 的嵌套方式。读图就是沿着轨道走；画图就是把语法规则翻译成路径。

这里的“节点是语法元素”需要再分细一点。query、sort、{ 和 , 是终结符，最终会出现在输入中；QueryClause、SortValue 和 Number 是非终结符，只表示还要继续展开的语法类别。标准铁路图用两侧边界标记起点与终点；Mermaid 模拟版额外使用 start、end、选择 和 还有成员? 等辅助节点，它们不属于实际输入。

EBNF 是 Extended Backus–Naur Form 的缩写，中文通常译为“扩展巴科斯范式”。这里的 form 是“形式、记法”的意思，不是另外一个隐藏缩写；Backus–Naur 是人名。EBNF 用纯文本描述语法规则：左侧写语法类别，右侧写它允许展开成的结构。EBNF 不是轨道图，轨道图也不是 EBNF；前者是文字表示，后者是图形表示，两者可以表达同一套语法。

本文采用的是便于阅读的常见、简化的 EBNF-like 方言，而不是逐字符照抄某一个标准。它借用了传统 BNF 的 ::=、常见 EBNF 的引号和可选结构，并用 ( ... )* 表示重复。传统 BNF 常把非终结符写成尖括号，例如 <QueryClause> ::= ...；尖括号在这种记法中帮助读者识别非终结符。本文用不带尖括号的 QueryClause，用引号明确标出终结符，因此 QueryClause 与 "query" 的角色已经可以区分。ISO EBNF 也采用这种不要求尖括号的思路，并使用 =、;、逗号和 {...} 等自己的符号约定。不同资料中的 BNF/EBNF 记法并不完全统一，关键是同一份文档开头先声明并始终保持一套约定。

词法、句法与文法

lexical 和 syntactic 是两个层级的形容词。词法层从字符流中识别标识符、数字、关键字和标点等 Token；句法层再把 Token 组合成表达式、语句和更大的结构。return return 可以被词法分析器识别成两个关键字 Token，却不一定是合法语句，这正是两个层级的边界。

grammar 是名词，指规定合法形式的一组规则；grammatical 才是对应的形容词，表示某段输入符合这组规则。技术资料中的 syntax 有时泛指一门语言的全部形式结构，有时狭义地只指 Token 之上的句法，因此规范常用 lexical grammar 和 syntactic grammar 分别命名两层规则。

EBNF 是书写 grammar 的记法，而 grammar 定义了 syntax。EBNF 本身不限定终结符必须是哪一层：终结符是字符时，它可以描述词法；终结符是 Token 时，它可以描述句法。例如：

总图 B：同一规则的 Mermaid 模拟版

flowchart LR
    START((start)) --> LBRACE[左大括号]
    LBRACE --> HAS_MEMBER{有成员?}
    HAS_MEMBER -->|否| RBRACE[右大括号]
    HAS_MEMBER -->|是| MEMBER[TopLevelMember]

    COMMA --> MEMBER
    MORE -->|否| RBRACE
    RBRACE --> END((end))

这张总图和 EBNF 一一对应：左大括号、右大括号 和 逗号 是字面量；TopLevelMember 是待展开的非终结符；“有成员？”对应方括号表示的可选结构；“还有成员？”以及 逗号 → TopLevelMember 对应 ( "," TopLevelMember )* 的重复结构。后文的子图都从这个 TopLevelMember 占位节点展开，不需要把所有查询类型一次性塞进总图。

两版表达同一条规则，但采用不同图形约定。标准铁路图通过轨道分叉、旁路和返回路径表达选择、可选和重复；Mermaid 模拟版把这些结构写成菱形节点和带标签的箭头。本文的标准 SVG 图可以独立阅读，Mermaid 图用于对照和修改源码。

重复（repetition）是语法含义，例如 ("," TopLevelMember)*；返回轨道（loop）是表现重复的画法。递归（recursion）来自非终结符在展开过程中再次引用自身，通常保留为一个非终结符节点，再查阅对应子图。不能按“重复用 loop、递归用 back edge”划分标准轨道图的线条。

下面只讨论这张图的画法和读法，示例沿用原文中的 SearchRequestBody、TopLevelMember 和 QueryClause。

先分清：轨道图不是流程图

流程图通常描述“先做什么，再做什么”，节点是动作，箭头是时间或控制流。例如：

图 1：流程图与轨道语法图的语义差异

flowchart LR
    A[接收请求] --> B[解析 JSON] --> C[执行查询] --> D[返回结果]

轨道图描述“输入可以长什么样”，节点是终结符、非终结符或辅助控制节点，箭头是合法路径。例如，下面的图不是在说 Elasticsearch 先执行 query 再执行 sort，而是在说一个请求对象可以同时包含这两个成员：

图 2：请求对象中顶层成员的重复路径

flowchart LR
    START((start)) --> LBRACE["{"] --> MEMBER{选择成员}
    MEMBER --> Q[query]
    MEMBER --> SORT[sort]
    Q --> MORE{还有成员?}
    SORT --> MORE
    MORE -->|是| MEMBER
    MORE -->|否| RBRACE["}"]
    RBRACE --> END((end))

query 和 sort 在 JSON 中是同级字段。它们在轨道图里先后出现，只是因为图需要把“多个成员”画成一条可行走的路径，不代表搜索执行有这个先后顺序。

三个快速判断

判断一张图是不是轨道图，可以看三个地方：

问题 轨道图的答案 流程图的答案
节点表示什么？ 字面量、语法类别或占位符 动作、状态或系统组件
箭头表示什么？ 输入的合法排列方向 时间、控制流或数据流
回路（loop）表示什么？ 重复出现、列表或递归 重试、循环或事件回环

节点是语法符号，箭头是合法输入路径。回路（loop）是图形上的返回路径，通常表达同一层结构的重复；递归则是一个非终结符在展开过程中再次进入自身。若节点是动作、箭头表示先后，才是流程图；若节点是数据对象、箭头表示传递，才是数据流图。

轨道图的节点与轨道

标准铁路图主要包含终结符、非终结符、边界标记，以及把它们连接起来的轨道。选择和重复可以直接用线条表达。Mermaid 模拟版额外增加判断节点，以适应流程图的布局。

起点和终点

start 和 end 表示一条完整路径的边界。它们不属于输入内容，只告诉读者从哪里开始走、走到哪里算完成。

图 3：完整路径的起点和终点

flowchart LR
    START((start)) --> TOKEN[一个合法输入] --> END((end))

如果一张图没有清楚的起点，读者不知道哪些节点是必经的；没有清楚的终点，读者也无法判断某个分支是否已经组成了完整结构。

字面量节点

字面量是输入中真的要出现的字符或单词，例如 {、}、query、,。在 Mermaid 中可以用方框表示：

图 4：字面量与语法类别的组合

flowchart LR
    START((start)) --> LBRACE["{"] --> KEY["query"] --> COLON[":"] --> VALUE[QueryClause] --> RBRACE["}"] --> END((end))

这张图对应一个最小请求：

其中 QueryClause 不是要原样输入的字符串，而是一个需要继续展开的语法类别。

语法类别节点

QueryClause、SortValue、TopLevelMember 这类名称是非终结符（non-terminal）：它们代表一组可能的结构，不能只看名字就算走完。

图 5：非终结符的候选展开

flowchart LR
    A[TopLevelMember] -.展开.-> B{选择一种成员}
    B --> C[query : QueryClause]
    B --> D[sort : SortValue]
    B --> E[size : Number]

图中 TopLevelMember 是一个入口，右侧分支列出它允许的具体形状。非终结符的价值在于复用：同一个 QueryClause 可以被根查询使用，也可以被 bool.must 的子查询使用。

选择、重复和回到入口

标准铁路图的选择由分叉和汇合的轨道表示，可选结构增加一条绕过内容的旁路，重复结构增加一条返回入口的轨道。下面的 Mermaid 模拟图才使用菱形和“还要一个？”标签；这些辅助节点不属于标准铁路图的必要构件。

图 6：选择分支与重复回路（loop）

flowchart LR
    CHOICE{选择}
    CHOICE -->|A| A[A 分支]
    CHOICE -->|B| B[B 分支]
    A --> MORE{还要一个?}
    B --> MORE
    MORE -->|是| CHOICE
    MORE -->|否| END((end))

这张图表达的是“可以选择多个成员”，而不是“先执行 A，再执行 B”。如果回路（loop）上没有“是/否”“逗号后继续”或“重复一次”等说明，读者很难知道回路的边界，画图时应补上标签。

这几行不是 Elasticsearch 的配置，也不是可直接提交的 Query DSL，而是帮助画图的语法摘要。判断一个符号怎么使用，不能只看它的形状，还要看它在规则中的位置：

符号 含义 使用判断
::= 左侧可以展开成右侧 定义一个语法类别，例如 QueryClause ::= ...
` ` 候选分支
[ ... ] 可选，出现零次或一次 结构可以省略，例如请求体可以没有 TopLevelMember
( ... )* 括号内的结构可以重复零次或多次 重复的是整个括号内结构，例如 ("," TopLevelMember)* 每次重复都包含逗号和一个成员
"..." 输入中要出现的字面量 要求输入出现这段固定文本，例如 "query"、"{"、","；引号表示它是字面量，不表示它不能重复
首字母大写的名称（通常为 PascalCase） 还需要继续展开的语法类别 例如 QueryClause、Number；它们不是要原样输入的字符串

模式：可选的分隔列表 [X ("," X)*]

规则里反复出现同一个形状：SearchRequestBody 的成员、BoolBody 的成员、ChildQueryValue 的数组元素，以及后文 JSON object 的成员。它要同时满足三点：元素可以有零个或多个；相邻元素之间必须有逗号；逗号不能出现在开头或结尾。几种看起来更短的写法各差一点：

写法 能生成 问题
X* {}、{ a b } 表达不了逗号
(X ",")* { a, b, } 末尾多一个逗号，JSON 不允许
("," X)* { , a, b } 开头多一个逗号
X ("," X)* { a }、{ a, b } 正确，但至少要有一个元素
[X ("," X)*] {}、{ a }、{ a, b } 正确，允许空

关键在于把第一个元素单独提出来：X ("," X)* 读作“一个元素，之后每多一个元素就先写一个逗号”，逗号因此只会落在两个元素之间。它表达的是“一个或多个”。外面再套一层表示零次或一次的 [ ]，就把“一个或多个”变成了“零个或多个”，得到空对象 {}。ChildQueryValue 的数组分支没有套 [ ]，所以 "must": [] 这种空数组不在本文文法的合法路径上。

在铁路图里，这个模式对应一条返回轨道，逗号就画在返回轨道上（tabatkins railroad-diagrams 中的 OneOrMore(item, separator)），再加一条跳过整段的上方旁路（Optional）。图 9A、图 11A 和图 12A 的下方返回轨道都是这样画的。

引号和重复次数是两件事。逗号字面量虽然带引号，但它位于 ("," TopLevelMember )* 中，所以可以随着回路出现多次；相反，一个没有引号的 QueryClause 是非终结符，必须根据它的定义继续展开。| 也不是“把几段文字都连接起来”，而是一次展开时从候选分支中选择一个。

在 QueryClause 的 QueryType 位置，match 和 bool 都是并列可选的查询类型：

这里有两个需要同时记住的层次：

  • 语法层面，match 和 bool 都可以填入 QueryClause 的 QueryType 位置。
  • Elasticsearch 的查询分类层面，bool 是一种 compound query，因为它可以通过 must、filter、should 和 must_not 组合子查询；match 通常是叶子查询。

所以，match 和 bool 可以互换的是“查询类型的位置”，不能直接互换查询体。选择 bool 后，需要继续展开它的组合查询结构；选择 match 后，通常沿字段和值走到叶子。

这里的“可以互换”有一个边界：凡是语法规则要求一个 QueryClause 的位置，都可以放一个以 bool 为 QueryType 的查询子句，也可以放一个以 match、term 或其他查询类型为 QueryType 的查询子句；反过来，bool 也只能出现在这些 QueryClause 插槽中。也就是说，同一个查询子句位置可以选择 bool 级别的组合查询，也可以选择叶子查询，但这不意味着 bool 可以替代 Number、SortValue，或字段名 "query"、"must"。

主轨道：请求对象的边界

SearchRequestBody 的主干只有三个部分：左大括号、成员、右大括号。

图 7：SearchRequestBody 的最小主轨道

flowchart LR
    START((start)) --> LBRACE["{"] --> MEMBER[TopLevelMember] --> RBRACE["}"] --> END((end))

这张图只表达一个成员。规则中的 ("," TopLevelMember)* 表明第一个成员之后还可以添加“逗号 + 新成员”。

非终结符展开：保留入口，另画子轨道

TopLevelMember 不是要原样输入的文本，而是主轨道上的一个非终结符入口。展开它时，通常不把整个子图硬塞回图 7，也不把图 7 的节点物理替换成一大段新连线。更清楚的做法是保留图 7 作为总览，再为 TopLevelMember 单独画一张子轨道；阅读时把图 7 中的 TopLevelMember 连接到这张子图的 start。

因此，展开不是“在原图上再走一遍”，而是“从占位节点跳到它对应的定义”。只有规则很短时，才适合把展开结果直接内嵌在原图中。规则较复杂时，分层画图能让每张图只承担一个语法类别。

这一步应明确记录在画图流程中：

  1. 先画 SearchRequestBody 的主轨道，把 TopLevelMember 保留为占位节点。
  2. 再画 TopLevelMember 的子轨道，把它展开为 query、sort、from 和 size 四个候选形状。
  3. 选择 query 分支后，继续跳到 QueryClause 的子轨道；QueryClause 再选择 BoolClause 时，继续进入 BoolBody、BoolMember 和 ChildQueryValue。

回路（loop）：重复成员

图 9A：顶层成员的标准铁路图

标准版保留了空对象旁路。下面的 Mermaid 图单独展示“已有一个成员后继续添加”的非空路径，因此省略了旁路。

图 9B：顶层成员非空重复路径的 Mermaid 模拟版

flowchart LR
    START((start)) --> LBRACE[左大括号] --> MEMBER[TopLevelMember] --> MORE{还有成员?}
    MORE -->|是：先写逗号| COMMA[逗号]
    COMMA --> MEMBER
    MORE -->|否| RBRACE[右大括号]
    RBRACE --> END((end))

沿着“否”走，得到只有一个成员的对象；沿着“是”走一次，再选择一个 TopLevelMember，就得到包含两个成员的对象。继续走回路（loop），就得到三个或更多成员。

query、from 和 size 是三个不同的 TopLevelMember，它们可以沿着同一条回路（loop）依次出现。

分支：选择成员形状

TopLevelMember 有多个候选形状，因此从选择点分出多条轨道：

图 10A：TopLevelMember 的标准铁路图

从入口选择一条轨道，经过字段名、冒号和字段值，再汇合到出口。字段名终结符中显示的双引号属于实际 JSON；EBNF 中用于界定字面量的引号则是文法记号。本文其他 EBNF 简写省略了这一词法层细节。

图 10B：TopLevelMember 的 Mermaid 分支概览

flowchart TB
    MEMBER{选择 TopLevelMember}
    MEMBER --> Q["query : QueryClause"]
    MEMBER --> SORT["sort : SortValue"]
    MEMBER --> FROM["from : Number"]
    MEMBER --> SIZE["size : Number"]

分支的含义是“选其中一个形状”，不是“这些字段都必须出现”。字段是否可选、是否能重复，需要由外层轨道表达。这里的外层回路（loop）允许不同成员继续出现，但没有表达“同名字段能否重复”；如果规则禁止重复 key，就应在文字说明中明确这一点，不要让读者从回路（loop）猜出错误结论。

非终结符引用：递归子查询（recursion）

bool 的 must、filter、should 和 must_not 可以承载一个或多个查询子句。子查询本身仍然是 QueryClause，所以它可以再次选择 match、term 或另一个 bool。

图 11A：子查询值的标准铁路图

这张图允许一个 QueryClause，或一个由逗号分隔的非空 QueryClause 数组。数组下方的返回轨道只负责重复数组元素。

图 11B：bool 子查询成员的标准铁路图（代表性分支）

这张图定义一个 bool 成员，不是完整 bool 对象；bool 还支持其他参数。结合图 8A、图 11B 和图 11A，引用链是 QueryClause → BoolClause → BoolBody → BoolMember → ChildQueryValue → QueryClause。BoolBody 用的是前面的可选分隔列表模式："{" [BoolMember ("," BoolMember)*] "}"。递归体现在这些语法定义相互引用，单张标准铁路图不需要画一根返回父图的线。

图 11C：查询类别递归引用的 Mermaid 关系图

flowchart LR
    ROOT[QueryClause] --> TYPE{选择 query type}
    TYPE --> LEAF[match / term / range]
    TYPE --> BOOL[bool]
    BOOL --> SLOT[must / filter / should / must_not]
    SLOT --> CHILD[QueryClause 或 QueryClause 数组]
    CHILD -.再次展开.-> TYPE

这里的递归路径需要按“字段名 → 字段值 → 字段值的语法类别”来读，而不是把每个单词都看成同一种节点：

对应到 JSON：

query 是顶层对象中的字段名；它的字段值是一个 QueryClause。这个 QueryClause 展开成一个对象，并选择 bool 作为 QueryType。bool 对应的 BoolBody 再展开出一个 BoolMember，即 must 字段，而 must 的字段值属于 ChildQueryValue。这里选择数组形式，数组中的每个元素又是一个 QueryClause；第一个元素选择 match，在叶子处结束。

上面的示例已经展示了“父 QueryClause 包含子 QueryClause”，但子句选择的是叶子类型 match。如果要展示 QueryClause 到 QueryClause 的递归，可以让 must 数组中的子句再次选择 bool：

这里不能在 must 数组元素外再写一层 "query"。"query" 只属于最外层的 TopLevelMember；must 数组中的元素直接是 QueryClause。因此，递归路径是：

第一层 QueryClause 选择 bool，must 引入第二层 QueryClause；第二层再次选择 bool，于是递归继续；当某一层选择 match、term 或 range 时，递归在叶子处结束。{ "query": { "bool": {} } } 不能作为这条递归链的示例，因为它既没有在 must 中提供子 QueryClause，也把只属于顶层的 query 字段放进了子查询位置。

因此，QueryClause → bool → must → ChildQueryValue → QueryClause 不是把同一个节点无条件地重复画一遍，而是由多个展开步骤组成。外层 QueryClause 的值选择 bool；bool 的值引入 must；must 的值引入子查询类别；子查询类别再次得到 QueryClause。如果子 QueryClause 再选择 bool，这条链可以继续递归；如果选择 match、term 或 range，就在叶子查询结束。

图 11C 的虚线表示“再次查阅查询子句的定义”，属于辅助关系图的注释约定。它不表示标准铁路图中的重复轨道，也不表示查询执行时无限循环。每次嵌套对应一个实际的子查询对象，有限输入的展开也必须结束。

例如，下面的 bool 嵌套了两个叶子查询：

重复（repetition）和递归（recursion）确实需要区分，但它们描述语法结构，不对应两种标准回边。图 9A 的下方返回轨道重复同层成员；图 11A 的下方返回轨道重复数组元素。两处都使用相同的铁路图构件。

图 11A 中的 QueryClause 是对语法定义的引用。沿着 bool 查询体继续展开后再次引用 QueryClause，才形成递归。标准图把这个引用保留在非终结符框内；图 11C 为了说明引用链额外画了虚线，它是一张关系图，不能把这条虚线当成铁路图特有的“递归回边”。

这里不采用 repetition loop 与 back-edge loop 两分法，也不靠实线、虚线判断重复和递归。若使用“回边”一词，只把它当作“向前方入口返回的线”的口语描述；它也不能直接等同于 DFS 或 JVM 控制流中具有各自定义的 back edge。“回边计数器”属于对应算法或虚拟机的语境，应按那里实际统计的边来理解。

用轨道图定位常见误读

把同级参数看成执行顺序

图上从 query 走到 sort，不表示先执行查询再执行排序。它只表示 JSON 对象可以先写 query，再写 sort。把两个字段交换顺序，仍然可以得到同样结构的请求。

把分支看成同时发生

TopLevelMember 的分支是“选择一个成员形状”。一次经过选择点只能走一条分支；要同时拥有 query 和 size，必须回到“还有成员”的回路（loop），再走一次选择点。

把递归引用（recursive reference）看成无限循环

QueryClause → bool → child QueryClause → QueryClause 是语法递归。它表达“查询可以嵌套查询”，不代表 Elasticsearch 会无限执行。真正的输入总是有限 JSON，解析树也会在叶子查询或其他终止节点结束。

把占位符当成字面量

QueryClause、Number 和 SortValue 不是要原样输入的字符串。只有带引号的 {、}、query、, 等才是字面量。把 QueryClause 写进 JSON，会得到一个示意文本，而不是可执行请求。

把代表性分支当成完整清单

图里常写 match / term / range / ...。省略号表示还有其他合法类型，不表示列表已经穷举；图题应标明这是代表性结构，而不是版本无关的完整规范。

标准 SVG 与 Mermaid 模拟版的取舍

标准 SVG 版通过专用铁路图生成器绘制，使用顺序（sequence）、分支（choice）、可选（optional）和重复（one or more）构件。SVG 是独立矢量图片，无需浏览器运行 Mermaid，也能保留平滑弯轨和旁路。本文图源定义保存在仓库的 tools/render-query-dsl-railroads.mjs 中。

JSON.org 的对象图可以用相同画法重画如下，忽略词法层的空白字符：

图 12A：JSON object 的标准铁路图

上方旁路对应 [ ... ]，下方经过逗号的返回轨道对应重复部分。value 可以继续展开成对象或数组，这种嵌套来自非终结符引用，不要求再增加一种专门的“递归轨道”。

用 Mermaid 模拟语法关系

本文的 Mermaid 版本使用 flowchart 模拟语法关系。菱形和“是／否”标签是这种模拟方式的辅助记号；需要标准铁路图外观时，使用前面的 SVG 版本。下面仅演示分支与重复构件，不是图 12A 的 JSON object 文法。

图 12：用 Mermaid 模拟轨道图的基本结构

flowchart LR
    START((start)) --> A[必经字面量]
    A --> CHOICE{选择}
    CHOICE -->|一种| B[候选 A]
    CHOICE -->|另一种| C[候选 B]
    B --> MORE{重复?}
    C --> MORE
    MORE -->|是| COMMA[逗号]
    COMMA --> CHOICE
    MORE -->|否| END((end))

画图时保留三条约束：

  1. 起点和终点只出现一次，字面量、语法类别和选择点使用稳定的形状。
  2. 分支箭头写清选择条件，回路标明重复条件。
  3. 递归关系图的引用箭头标明“再次展开”，与表示重复的返回轨道分别说明。

如果一张图已经需要大量颜色图例、跨页连线和长段落注释，说明它可能塞进了过多规则。拆成“请求体主轨道”“查询子句轨道”“具体 query type”三张图，读者更容易沿着一条路径验证一个问题。

画完后的验证

画完后，沿着图至少走出三条路径：

路径 应验证的内容
最短路径 能否生成最小合法输入
一次重复路径 回路（loop）是否真的能增加第二个元素
一次递归路径 子查询是否能回到同一语法入口并在叶子处结束

再检查四个边界：

  • 是否把语法关系误画成执行顺序？
  • 是否把可选项误画成必选项？
  • 是否把递归误画成无条件循环？
  • 是否把代表性示例误写成完整规范？

轨道图的核心不是“画得像铁路”，而是每条合法路径都能回译成一个输入实例，每个不合法结构都能指出卡在哪一段轨道上。用这个标准检查《查询与检索》中的 Query DSL 图，query、sort、bool 和 child QueryClause 各自处于哪一层，就能沿路径验证。
