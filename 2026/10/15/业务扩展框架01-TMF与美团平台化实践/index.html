业务扩展框架01：TMF与美团平台化实践解决什么问题

Created2026-10-15|Updated2026-10-18|系统架构
|Word Count:5.1k|Reading Time:16mins|Post Views:

多业务共用平台以后，复用为什么会变难

一个订单平台同时支持普通零售、预售和团购。三者都有商品、价格、订单与库存，但预售需要校验销售时间和预售额度，团购需要校验成团条件，普通零售通常直接处理现货。把共同步骤提取出来并不难，难的是下一次改预售规则时，怎样确定团购完全不受影响。

最直接的写法是在每个步骤判断业务类型。业务增多后，条件会散落到价格、库存、退款、消息消费等位置。新增业务的代价不只是多写几个分支，还包括找到所有分支、理解组合顺序、协调多个团队发布，以及证明旧业务没有改变。

将分支改成若干 Strategy 类，只解决了代码摆放。若每个策略自行判断是否适用、彼此没有清晰归属，两个策略可能同时生效，运行时仍然需要回答：这次请求应执行谁，为什么，冲突时怎么办。

TMF 一类业务扩展框架要把这些关系显式化：平台定义稳定的业务契约和变化点，业务提供定制实现，配置表达安装关系与冲突决策，运行时按明确的业务上下文执行。它需要的前提是已经存在值得复用的业务模型；框架不会从一堆任意 Java 方法中自动发现一个交易平台。

本系列分为三篇：

  • 本篇：TMF 与美团公开实践的目标、领域模型和架构边界。
  • 第二篇：注解究竟描述什么，静态元数据怎样与动态配置协作。
  • 第三篇：运行 Java mock，并用 Lattice、OCTO、ServiceComb 检验远程绑定。

已有的 《插件化架构》 可以作为概念索引。本系列中的厂商事实以公开原始资料为准，教学模型与代码单独标明。

TMF、BPF与公开证据的边界

TMF 通常指阿里交易模块化框架 Trade Modularization Framework。2018 年的公开介绍强调业务插件与平台分离、统一业务身份，以及管理域和运行域分离；2021 年设计者毗卢的文章进一步解释这些设计如何处理业务规则归属与协作问题。文章描述的是当时的架构，不能直接当成 2026 年阿里内部的现状。阿里技术：TMF2.0 介绍、毗卢：TMF2.0 的关键设计要点。

“美团 BPF”在部分二手文章里与 TMF 并列，但截至 2026-10-15，本次检索未获得足以确认其正式全称、统一 API 和源码版本的一手证据。这不构成“BPF 不存在”的结论。可核验的美团材料包括 Camp 广告平台化、BFF 组装式架构和交易系统领域建模，下面按各自公开名称讨论，不把它们合并为一个叫 BPF 的框架。

TMF2 设计者后来公开了 Lattice，并将其定位为简化的相关实现。Lattice 的文档、注解与示例可供验证机制，但不能据此把 Lattice 的类名反写成内部 TMF2 的类名。Lattice 开源说明、项目仓库。

这几种证据分别支持架构意图、公开产品的 API，以及自建示例的运行行为。它们无法证明内部生产环境的性能、发布隔离程度或故障恢复效果。

从业务动作到扩展点

以教学用的预售下单为例，平台对外提供“创建订单”。调用方不需要先知道价格域有多少策略，库存域部署在哪台机器。平台内部再把请求组织为校验、计价、额度处理、订单持久化等动作。

这些名词需要在各自层级上定义：

概念 教学场景里的例子 主要回答的问题
业务活动、领域服务 用户下单、创建订单、计算应付金额 系统向调用者提供什么完整动作
领域能力 订单计价、销售资格判断、库存预留 哪种业务语义可以稳定复用
扩展点 计价中的单价策略、资格判断中的渠道限制 哪一部分允许业务定制
扩展实现 预售价、团购价、预售时间校验 某种差异具体怎样计算
商业产品 预售、团购、电子凭证 哪些跨步骤规则组成可重复使用的业务方案

这是一套用于解释的分层，不要求每层都对应一个 Java 包、接口或微服务。一个小系统可以只保留领域服务和扩展接口；为了对齐名词而建立大量空壳，只会增加跳转成本。

领域能力也未必就是扩展接口。订单计价能力可以包含金额校验、币种一致性、舍入规则和多个可变策略。能力的公共实现维持不变量，扩展点只开放允许变化的部分。若任何插件都能覆盖订单总额、跳过资金约束，平台就没有留下可依赖的交易语义。

业务身份怎样关联商业产品

业务身份是路由规则所使用的稳定分类，不等于用户 ID、租户 ID、订单 ID，也不等于机器地址。教学示例用 retail、presale、group 作为三个身份；实际交易模型可能从市场、渠道和商品属性中识别业务。

TMF 的公开模型区分垂直业务与可叠加的水平产品。业务身份关联可用的产品组合，某个产品本次是否生效还可能取决于业务会话。一个垂直业务采用电子凭证能力，并不意味着每笔订单都选择电子凭证。Lattice：业务概念。

因此至少存在两道选择：

业务身份不应成为无限拼接的字符串。把行业、会员等级、促销活动、地域、渠道全拼进一个 code，容易形成组合爆炸。较合理的教学建模是：用业务身份选择规则空间，用产品配置表达可复用方案，用请求属性参与条件判断。哪些维度属于身份，要根据领域中的管理责任和隔离要求决定。

商业产品也不等于面向消费者售卖的 SKU。“预售”可以是平台内部的一套方案，跨计价、库存和履约分别提供实现。某个实现是否由平台团队维护，不改变它的归属：平台维护的通用预售规则仍可以作为可选产品被不同业务安装。

业务身份的传递必须有可信来源。Web 入口可根据已认证的应用和商品归属解析身份，并将结果随命令传递；异步消息需要保留重建业务上下文所需的信息。不能让调用方随意传 bizCode=privileged 就启用更宽松的规则。统一业务身份解决分类与关联，授权仍然是独立职责。

代码定义回答“有哪些能力和实现”，配置回答“谁采用谁”，请求上下文回答“这次适用谁”。这三份信息合起来才足以执行。

管理域可以提前发现未知能力、缺失配置、重复实现和可静态识别的规则冲突。运行域仍然需要计算金额、检查资格、访问库存。所谓静态期决策，不是把所有业务计算都提前算完，而是尽量提前确定可用规则、组合关系和冲突处理方式。

平台团队的责任也因此更具体：维护语义稳定的契约、验证候选配置、给出默认行为、解释实际路由结果。业务团队在这个契约内实现差异。代码仓库分开只是开发隔离；如果所有插件仍共享一个 JVM、线程池和发布进程，资源与故障隔离并没有自动完成。

美团公开实践展示了两种不同的组合方式

Camp：能力目录与数据依赖图

美团外卖广告的 Camp 文章公开了 @LppAbility 与 @LppExtension。前者描述原子能力，后者描述具体扩展；框架在编译阶段采集元数据。它还分析 Action 的数据依赖以构建 DAG，再由场景配置和调度执行组合结果。美团：广告平台化的探索与实践，2022-03-03。

这个方案提示了一种重要区别：能力选择关注用哪个实现，DAG 编排关注执行先后与可并行关系。接口实现可替换，不代表执行图已经确定。

BFF：复用预组装结构，选择场景子图

美团的 BFF 文章使用统一业务身份关联组件组装 DSL 和配置，并讨论从预组装活动图中选择所需子图。它针对的是跨领域的数据查询和展示组装，不能直接搬成交易写入的事务模型。美团：标准化思想及组装式架构在后端 BFF 中的实践，2022-04-28。

例如“带筛选的商品货架”与“不带筛选的商品货架”，可以共用商品查询和卡片组装，只在前者激活筛选数据组件。这是对既有组合空间的选择，通常比允许任意拖动所有节点更容易验证。

广告数据流、展示活动图、交易规则叠加，都可能采用组件和配置，却不应被强行压成同一套扩展模型。场景决定组件颗粒度、输入输出契约以及失败语义。

复用的上限由契约决定

新业务能够只改配置，至少意味着所需能力已经存在、输入输出兼容、执行顺序合法、组合没有破坏不变量。任一条件不满足，仍然需要新增代码或调整领域模型。

  Need["新业务需求"] --> Exists{"所需能力与实现<br/>已经存在？"}
  Exists -->|是| Types{"输入输出类型<br/>及业务含义兼容？"}
  Types -->|是| Order{"既有编排能表达<br/>合法执行顺序？"}
  Order -->|是| Rules{"状态与补偿语义已定义<br/>且不变量可保持？"}
  Rules -->|是| Configure["配置安装关系与规则<br/>完成组合验证后发布"]
  Exists -->|否| Develop["补充代码或调整领域模型<br/>重新验证"]
  Types -->|否| Develop
  Order -->|否| Develop
  Rules -->|否| Develop

例如把既有团购计价与既有预售额度组合起来，并不能自动得到“预售团购”。还需要确定成团失败是否退订金、预售额度何时释放、尾款逾期如何处理。这些状态和补偿语义若未定义，几个插件都成功执行也不能证明业务正确。

扩展点过细还有反作用：一个金额计算过程拆成几十个只返回配置值的方法，会让调用者难以理解整体行为。阿里公开的架构反思直接讨论过细粒度扩展点带来的理解和维护成本。阿里云开发者：业务系统架构实践总结，2023-09-28。

判断一个能力是否值得复用，可以比较两个业务的输入含义、结果含义和变化责任。两处代码都返回“10 分钟”不是复用证据；它们是否应在同一业务规则变化时一起改变，才有助于确定边界。
