成功输出以外还需要验证什么

实验主程序的断言按行为组织：

场景 预期结果 要防止的错误
未知业务或不存在的配置引用 拒绝请求或拒绝发布 拼错配置却使用默认逻辑
SINGLE 最高优先级并列 拒绝执行 依赖类加载或 Map 顺序碰巧选中
没有适用计价候选 使用唯一默认价 缺省行为含混
已选计价实现抛异常 异常继续传播 依赖故障被伪装成正常原价
非法发布与合法新版本 非法版本不替换；请求使用一次取得的快照 请求混用不同版本的产品和规则

金额校验额外覆盖负数、按分舍入和大整数。计算折扣使用 BigDecimal，最终转换为 long 分；避免先用 long 乘百分比造成中间溢出。

实验的快照测试证明已有请求对象持有固定引用，以及非法发布后旧快照仍可用。它没有做多进程一致性或并发压力测试。两个应用各自更新到不同版本的问题，不能靠单 JVM 的 AtomicReference 解决。

ALL 顺序执行也不意味着事务。如果第二个库存动作抛异常，第一个动作的副作用可能已经发生。当前 mock 只记录事件，没有真实扣减，因此不会产生库存损失；生产系统需要独立设计幂等、持久化状态与补偿。

接口与实现究竟有没有远端绑定

需要分别回答两个问题：

注册表可以返回直接执行本地逻辑的实现，也可以返回封装远程调用的客户端或代理。是否跨进程，取决于调用链是否发送网络请求；代理本身也可以只做日志、鉴权或本地路由。

JDK 动态代理把接口方法调用交给 InvocationHandler；处理器可以直接调用本地对象，也可以编码请求并交给 RPC 客户端。JDK Proxy 文档。本实验直接调用本地 Action，没有伪装成已经实现 RPC。

Lattice：有明确的远程扩展机制

Lattice 的 2022-10-01 教程展示了 protocolType = ProtocolType.REMOTE。调用方使用远程客户端与 Dubbo runner，另一进程运行插件容器，业务实现部署在那里。教程提供了使用 Dubbo、Nacos 的样例，而不是 Java RMI。Lattice：RPC 调用扩展点、远程示例仓库。

该版本文档还限制 REMOTE 的业务叠加，并建议必要时在远端容器内部完成本地叠加。这是有意限制远程调用规模的设计，不能把本地多实现归约无条件搬到网络上。

OCTO：从接口调用进入服务治理与通信链

OCTO 是美团公开的微服务通信与治理体系。它的 Appkey、服务实例发现、路由与负载均衡解决远端服务定位问题；这些对象并不天然包含“预售产品安装哪些业务能力”。美团 OCTO 开源介绍，2019-08-08。

公开 Dorado 源码可以确认一条具体链路。在提交 b7aaefe900368cfc4edf1fd793a2521e9f48aec1 中，JdkProxyFactory 调用 Proxy.newProxyInstance，把接口代理绑定到 DefaultInvocationHandler；后者将方法与参数封装为 RpcInvocation，交给 handler 处理。

  • JdkProxyFactory.java，固定提交。
  • DefaultInvocationHandler.java，固定提交。

接口在调用方得到的是代理，真正的业务处理在远端进程完成。代理提供相似的调用语法，却不能消除网络失败、超时和重复请求。

Dorado 还把代理工厂等基础设施定义为 SPI 扩展。这与“根据业务身份挑选预售价”处于不同层次：前者决定框架如何生成代理或如何通信，后者决定业务采用什么规则。ProxyFactory.java、OCTO-Dorado 官方 Wiki。

华为云 CSE 与 ServiceComb：服务引用注解的对照

华为云 CSE 的公开定位包括注册发现、配置管理和服务治理，并支持 ServiceComb 等生态。这里选用 Apache ServiceComb 的公开文档作对照，不推断华为内部存在与 TMF 相同的业务产品模型。华为云：什么是微服务引擎。

它与 @Extension(id="presale-price", point=PRICE) 的建模对象不同：一个描述服务引用，一个描述本地业务扩展实现。业务组件可以依赖远程引用，但不能因此把远程引用本身解释为领域能力组合。

与RMI相似的部分，及其失效的地方

RMI 与这些 RPC 方案都可以让调用方通过接口或代理发起调用，参数被传到另一个进程执行。相似性停留在远程调用抽象；Java RMI 有自己的远程对象与调用体系，OCTO 使用其通信协议和治理机制，Lattice 示例接入 Dubbo。不能因为“像调用本地接口”就把它们称为 RMI。Java RMI 系统概述。

把业务组件远程化后，至少增加三个必须明确的契约：

  1. 调用结果未知时如何处理。客户端超时可能发生在远端完成写入之后，重试需要幂等键或可查询的执行记录。
  2. 上下文如何跨进程传递。业务身份、租户、trace 和配置版本的语义需要双方约定；传一个同名字段不等于双方规则一致。
  3. 失败能否降级。资格校验或价格计算失败后使用默认实现，可能改变商业结果，必须由业务契约明确授权。

网络开销也会影响扩展颗粒度。一个领域能力内部十个细小扩展点若各自跨进程，调用数量、失败概率和版本兼容面都会扩大。将具有一致事务或数据需求的一组规则放在同一个远程边界内，通常更容易管理；最终仍需要实际延迟与失败预算验证。

一条可实施的组合链路

图 5 是基于前述机制推导的架构，不代表已证实的 BPF 内部实现：

图 9：业务规则选择与远程服务定位分层的教学架构。

flowchart TB
  accTitle: 业务规则选择与远程服务定位分层的教学架构
  Request["可信业务身份与请求事实"] --> Config["业务配置版本"]
  Config --> Product["激活产品与能力"]
  Product --> Policy["选择业务扩展实现"]
  Policy --> Local["本地计算"]
  Policy --> Adapter["远程服务适配器"]
  Adapter --> Proxy["RPC接口代理"]
  Proxy --> Discover["服务发现、路由、实例选择"]
  Discover --> Remote["远端领域服务"]

适配器对上保持领域契约，对下使用 OCTO、ServiceComb 或其他 RPC 客户端。业务身份在上层选择规则，服务标识在下层选择服务，实例选择再决定某台机器。三个决策可以关联，但不宜复用同一套命名和生命周期。

平台能力复用到这里仍有可观察的判据：相同实现是否被多个业务调用，路由是否能解释，新增配置是否通过契约测试，失败时是否保持预期语义。注解是建立目录的一种方式；是否能快速接入业务，要由这些行为证明。

实验范围

本次运行证明了单进程教学模型的组合、选择、默认与错误处理。Lattice 远程扩展依据公开教程，OCTO 代理链依据固定提交源码，ServiceComb 依据公开文档；未运行它们的跨进程环境。
