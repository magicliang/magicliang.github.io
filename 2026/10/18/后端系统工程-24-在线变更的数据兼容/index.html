后端系统工程 24：在线变更的数据兼容

Created2026-10-18|Updated2026-10-28|系统架构
|Word Count:6.7k|Reading Time:23mins|Post Views:

在线修改表结构时，系统里同时存在一份正在变化的表定义和至少两个版本的应用代码。旧代码按旧列读写，新代码按新列读写，后台回填任务又在补写历史行。三方都在提交事务，任何一方都可能把另一方刚写下的值改掉。DDL 本身还要拿表锁，一条看起来只改元数据的 ALTER TABLE 也可能让整张表的普通查询排队。

本篇用一张合成工单表，把“整数优先级”迁成“文本优先级”，并在迁移后期引入一个旧格式表达不了的新取值。要回答的问题有三个：回填期间新写入的值怎样不被覆盖；旧代码还在只写旧列时，新列怎样不落后；从哪一步开始，回退到旧代码就会丢语义，系统怎样拒绝一次假装无损的回退。实验结论都在本地 PostgreSQL 16.15 上用真实事务、真实线程和独立进程验证，证据在 evidence/24/；只引用文档、没有实验的论断在文中单独标出。

需求、不变量与范围

合成表 ticket 有主键 id、标题 title 和整数列 priority，取值 1、2、3。目标结构用文本列 priority_level 表示优先级，取值 low、normal、high，迁移后期再允许 urgent。映射固定为 1↔low、2↔normal、3↔high；urgent 没有对应整数，只能退化成 3。

迁移期间必须成立的不变量如下。

  • I1：回填不改写任何已经由业务写入新值的行。观察位置是逐行核对：每行 priority_level 等于该行最后一次已提交业务写入所期望的值。
  • I2：在越过不可逆点之前，旧列与新列表达同一个优先级。观察位置是校验查询 COUNT_MISMATCH（新列非空且不等于 lvl_of(priority) 的行数，另排除 urgent 与 3 的组合，越过不可逆点后这是合法映射）与 COUNT_NULL（新列为空的行数），两者都应为 0。
  • I3：一旦存在旧格式无法表达的值，回退守卫拒绝回退到旧代码，并报告无法表达的行数；收缩之后不存在数据库内的回退路径。

范围之外的内容：多副本与逻辑复制下的 DDL 传播、分区表、外部 schema 迁移工具、跨服务的数据契约。实验规模是教学假设：主用例 3000 行种子数据、4 个写线程，崩溃用例 4000 行、3 个写线程。实验不报告吞吐、延迟或 DDL 耗时，输出中的写入次数每次运行不同，只用来说明并发写确实发生过。

三个应用版本的读写契约

迁移期间同时存在三种代码，每种只认识自己那一部分结构。

表 24-1：各版本读写的列

版本 读 写 认识 urgent
v1（旧） priority 只写 priority 否
v2（双写） 切读前读 priority，切读后读 priority_level 同一条 UPDATE 写两列 否，传入 urgent 直接抛异常
v3（只写新列） priority_level 只写 priority_level 越过不可逆点之后

v2 的双写在一条语句里完成，所以两列要么同时更新，要么都不更新。v1 不知道新列存在，v3 不再维护旧列。两边各缺一半，缺口交给数据库内的兼容触发器补齐。

数据模型：新列、约束与兼容触发器

扩张阶段只加一个可空的新列和两条 CHECK：level_domain 限定取值集合，no_urgent_before_cutover 在越过不可逆点之前拒绝 urgent。把 urgent 的禁止条件做成数据库约束，而不只是应用里的判断，是为了让“能否撤回越过动作”也由数据库检查决定，后文的守卫依赖这一点。

这两条 CHECK 与加列写在同一条 ALTER TABLE 里，没有带 NOT VALID，PostgreSQL 会在持有 AccessExclusiveLock 期间扫描全表以校验既有行（DEBUG1 下可见 verifying table）。新列此时全为 NULL，CHECK 对 NULL 为真，扫描不会失败，但持锁时间随表大小增长。P4 为 NOT NULL 专门采用 NOT VALID 加 VALIDATE，同样的写法也适用于这里：两条 CHECK 加 NOT VALID，到 P4 一并 VALIDATE，语义不变。本章实现保留了带扫描的写法，表规模只有几千行，没有测量扫描时长。

兼容触发器按“本条语句改了哪一列”推导另一列：

这是 BEFORE INSERT OR UPDATE ... FOR EACH ROW 触发器。PostgreSQL 16 文档 43.10.1 说明，BEFORE 行级触发器返回修改过的 NEW，写入的就是修改后的行。v1 只改 priority，触发器补新列；v3 只改 priority_level，触发器补旧列；v2 两列都改，触发器不动。触发器不处理“本条语句没碰优先级”的情况，因此扩张之前就存在、此后没被业务改过的行，新列一直为空，这部分由回填负责。

另有两张辅助表：migration_state 是单行表，记录当前阶段与越过不可逆点的时间 no_return_at；backfill_progress 记录回填作业的断点 last_id、上界 max_id、已提交批次数与改写行数。

正常路径：并发写入下走完七个阶段

S1 用 3000 行种子数据，启动两个 v1 写线程，再在 P2 加入两个 v2 写线程。每个线程独占 id % 4 相同的行，所以同一行的写入顺序就是该线程的程序顺序，线程据此记下每行最后一次已提交写入的期望值，结束后逐行核对。线程还会插入新行，ID 从 100000 起。

回填用键集分页：每批的上界取断点之后第 250 行的主键。v1 在扩张之前插入的行 ID 从 100000 起，主键在 3000 与 100000 之间是空洞；按 last_id + 250 的固定步长切区间，会在空洞上提交大量不改任何行的批次。

DDL 本身的锁与扫描

迁移脚本里的每条 DDL 都要单独判断两件事：拿什么锁，是否扫描或重写整表。PostgreSQL 16 文档对 ALTER TABLE 的说明是：除非另有注明，各子形式都取 ACCESS EXCLUSIVE；多个子命令合在一条语句里时，取其中最严格的锁。

锁队列：一条排队的 ALTER 挡住后来的 SELECT

图 24-2：长事务、排队的 DDL 与后来的普通查询（S2 观察到的锁状态）

sequenceDiagram
    participant A as 长事务 A
    participant DB as ticket 表锁
    participant B as ALTER TABLE（B）
    participant C as 普通 SELECT（C）
    A->>DB: BEGIN; SELECT（AccessShareLock，granted）
    B->>DB: 请求 AccessExclusiveLock
    DB-->>B: granted=false，pg_blocking_pids(B)={A}
    C->>DB: 请求 AccessShareLock
    DB-->>C: granted=false，pg_blocking_pids(C)={B}
    A->>DB: COMMIT
    DB-->>B: 授予，ALTER 完成
    DB-->>C: 授予，SELECT 返回 100

S2 中，A 只执行了一次 SELECT count(*) 就停在事务里，持有 AccessShareLock。B 的 ALTER TABLE 等待 AccessExclusiveLock。随后到达的 C 只是普通查询，它请求的 AccessShareLock 与 A 持有的锁并不冲突，却仍被挂起。pg_locks 视图不暴露等待队列中的先后关系，文档建议用 pg_blocking_pids()；该函数把“排在前面、等待冲突锁”的进程也算作阻塞者（soft block）。输出中 C 的阻塞者正是 B：

阻塞者以会话的 application_name 显示：long-reader 是长事务 A，ddl 是 B。这一现象的成立条件是：存在一个持有任意表锁且不结束的事务，DDL 需要与之冲突的锁，并且没有设置超时。文档 13.3.4 节写明，只要没有检测到死锁，等锁的事务会无限等待。

lock_timeout：拿不到锁就退出队列

S3 在同样的长事务下，让 DDL 会话设置 lock_timeout = '300ms'。ALTER 在超时后以 SQLSTATE 55P03（lock_not_available）失败，退出等待队列；之后 C 的 SELECT 在长事务仍处于 idle in transaction 时就返回了。迁移脚本把 DDL 包在 withLockRetry 中：事务内 SET LOCAL lock_timeout，遇到 55P03 就回滚、退避后重试，其他错误直接抛出。用例在第二次失败后提交长事务，输出为 [1:55P03, 2:55P03]，第 3 次成功。

这里的保证只有一条：任何一次排队最多挡住后续查询 lock_timeout 那么久。lock_timeout 只限制排队时长；拿到锁之后，持锁期间的扫描（例如 P1 的 CHECK 校验）同样阻塞后续查询。如果长事务一直不结束，重试会耗尽次数，DDL 无法完成，此时要处理的是那个长事务。

ADD COLUMN：不带默认值或带非易变默认值时不重写表

文档 ALTER TABLE 的 Notes 写明：带非易变 DEFAULT 加列时，默认值在语句执行时求值并存入元数据，既有行读取时使用它；不带 DEFAULT 时为 NULL；两种情况都不重写表。易变默认值则需要重写整表及其索引。S4 用两个观察点核对：pg_class.relfilenode 是否变化，以及 client_min_messages = debug1 时服务端是否发出 rewriting table 消息。

不重写表不等于不拿锁。同一用例在事务内查询 pg_locks，ADD COLUMN 持有 AccessExclusiveLock 直到提交，所以它同样会陷入上一节的锁队列。

CHECK NOT VALID、VALIDATE 与免扫描的 SET NOT NULL

直接 SET NOT NULL 要扫描全表，并在整个扫描期间持有 AccessExclusiveLock。PostgreSQL 12 起，如果已有一个有效的 CHECK 能证明该列没有 NULL，扫描可以跳过。迁移中的做法是三步：先 ADD CONSTRAINT level_nn CHECK (priority_level IS NOT NULL) NOT VALID，它不检查既有行，加约束的 AccessExclusiveLock 只持有很短时间；再 VALIDATE CONSTRAINT，它扫描既有行，但文档说明只取 SHARE UPDATE EXCLUSIVE；最后 SET NOT NULL。

S5、S6 分别验证这三步。S5 的边界用例中，约束标为 NOT VALID 之后，更新一条尚未修复的旧行，哪怕只改别的列，也会因整行不满足 CHECK 而以 23514 失败。因此这条约束只能在回填完成之后再加，否则 v1 对未回填行只改其他列（例如标题）的更新会开始报 23514；v1 改优先级时，触发器先补上新列，不受影响。

负向对照说明，免扫描的前提是约束已验证（pg_constraint.convalidated = true），NOT VALID 的约束不算数。判断依据是服务端 DEBUG1 消息，消息文本可以在 16.15 的服务端二进制中找到；tablecmds.c 源码在本环境无法访问，本文没有引用源码中的控制流。SET NOT NULL 自身仍取 AccessExclusiveLock，免扫描只缩短持锁时间，排队问题仍然要靠 lock_timeout 解决。

CREATE INDEX CONCURRENTLY 失败后的 INVALID 索引

本次迁移不需要新索引，但切读之后按新列查询通常需要。文档说明，并发建索引先在目录里登记一个 invalid 索引，再分两个事务扫描表；扫描中出现死锁或唯一冲突时命令失败，索引留在目录里，查询会忽略它，写入却仍要维护它。S7 用一个重复值让唯一索引构建失败：

第四行是一个容易写进迁移脚本的错误：为了让脚本可重入而写 CREATE INDEX CONCURRENTLY IF NOT EXISTS，失败后重跑只收到一条 NOTICE，命令正常返回，索引依旧无效。文档对 IF NOT EXISTS 的说明是，不保证已有索引与将要创建的索引一致。所以脚本完成的判据应该是查询 pg_index.indisvalid，命令有没有报错不能作为判据。

后两行是绕过守卫、直接让 v1 上线的结果。v1 读到的 3 与真正的 high 无法区分；用户在 v1 界面把优先级改成 2 再改回 3，触发器按旧列推导出 high，urgent 就从数据库中消失了。这个点之后，“回滚”只剩两条路：继续向前修复，或者从越过之前的备份恢复并承担其后写入的损失。本章没有实现后者，也不把它当作无损回退。

回填进程在批次中途被杀

S11 让独立 JVM 回填进程每批在 UPDATE 之后、提交之前停顿 1 秒，同时运行 v1、v2、v3 三个写线程。父进程读到 IN_TX batch=4 时，确认数据库里该会话处于 idle in transaction，然后执行 kill -9：

客户端进程消失后，服务端会话随连接关闭而结束，未提交的第 4 批整体回滚。重启的进程从断点 600 继续，条件更新使重做的批次不会改写这段时间内业务写过的行。断点前进与数据改写在同一事务里，是续跑正确的前提。如果把断点写到另一个事务或外部文件，崩溃窗口里就会出现断点与数据不一致。

恢复流程

  • DDL 拿不到锁：55P03 回滚后退避重试；重试耗尽时用 pg_blocking_pids 找出持锁的长事务，处理该事务，不要去掉 lock_timeout 后直接重跑。
  • 回填中断：直接重启同一作业，断点在 backfill_progress，条件更新使重复执行无害。完成判据是 last_id = max_id、COUNT_NULL = 0、COUNT_MISMATCH = 0。
  • VALIDATE 失败：约束保持 NOT VALID，新写入仍受约束；修复违规行后再次 VALIDATE。
  • 并发建索引失败：按 indisvalid = false 找出残留索引，DROP INDEX CONCURRENTLY，修复数据后重建，以 indisvalid = true 作为完成判据。
  • 越过不可逆点之后需要回退：先尝试 uncross，它能成功就说明没有 urgent 行；失败则只能向前修复。收缩之后数据库内没有回退路径。

证据与限制

全部用例由 examples/schema-change/run.sh 一条命令运行，最近一次运行输出 SUMMARY passed=96 failed=0，退出码 0。S1–S10 属于真实组件实验，S11 属于多进程集成。以 negative control exposes 开头的负向对照共 8 处，另有 S6 的 NOT VALID 对照，每一处都真实观察到了错误结果。

这些实验不证明以下内容：多副本或逻辑复制环境下 DDL 与触发器的行为；REPEATABLE READ、SERIALIZABLE 下回填与业务写的交错（文档 13.2.2 描述为序列化失败，本章未实验）；更大表上 VALIDATE、重写和并发建索引的耗时；数据库服务端崩溃（本章只杀客户端进程）；真实滚动发布，三版本代码由同一 JVM 内的不同类模拟。“新旧代码并存时最多相差一个版本”的约束来自 F1 在线异步 schema 变更论文（Rae 等，PVLDB 6(11), 2013）：论文用 delete-only、write-only 等中间状态和 schema 租约保证同一时刻最多两个相邻版本在用，回填任务跳过回填开始后被用户事务更新过的行。本文借用了这些概念，没有实现租约与写栅栏，三版本共存的顺序由实验脚本控制。逐条边界见 evidence/24/LIMITS.md，来源见 SOURCES.md 的第 24 篇一节。
