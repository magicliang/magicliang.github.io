后端系统工程 33：通知渠道的结果未知

Created2026-10-18|Updated2026-10-22|系统架构
|Word Count:6.1k|Reading Time:21mins|Post Views:

通知服务调用外部渠道时，最难处理的结果是“没有结果”：请求发出去了，响应没回来。渠道可能根本没收到，也可能已经接受并开始外发，只是响应在路上丢了。本地数据库能把“同一事件只生成一条逻辑通知”做成硬约束，却无法替外部渠道保证“用户只收到一次”。本篇用一个最小通知服务把这两件事分开：逻辑去重由唯一约束负责，外部重复由渠道契约决定，结果未知要作为一种持久状态记录下来，并且有出口。

需求与范围

业务方提交事件，例如“订单 ord-1001 已发货”，通知服务按用户偏好为每个启用渠道生成投递任务，由工作进程领取后调用渠道。要满足的条件如下。

  • 同一 (user_id, event_key) 无论被提交多少次、多少并发，只产生一条逻辑通知。
  • 每条逻辑通知在每个启用渠道上最多一条任务；同一任务在同一时刻最多有一个有效令牌；被取代的持有者无法再改写任务状态，但它已发出的外部调用无法撤回。
  • 每次调用渠道都留下一条投递记录，结果未知的调用能在表里查到，不被后续结果覆盖。
  • 超时后的重试策略取决于渠道能力：支持幂等键就带同一键重发；不支持幂等键但可查询就先查询；两者都不具备就停止自动处理。
  • 领取前偏好被关闭则不发送；通知过了有效期则不发送。

排除项：投递回执、终端设备确认、渠道侧限流协商、模板渲染、退订链接。“SENT”在本篇只表示渠道接受了请求，与用户看到消息之间还隔着渠道自己的投递链路。

教学规模假设（不对应任何具体产品）：每分钟数百条逻辑通知，每条平均 1–2 个启用渠道，单个 PostgreSQL 实例，若干个无状态工作进程。在这个量级下，任务表加行锁领取足够，不需要额外的消息队列；需要改变这个判断的触发条件是单表领取的锁竞争或扫描成本成为瓶颈，本篇不测这一点。

外部渠道能承诺什么

先看标准里的接受语义。RFC 8030（Web Push）第 5 节规定，推送服务以 201 Created 表示消息被接受，并明确写出这“does not indicate that the message was delivered to the user agent”。同一 RFC 第 6.2 节要求用户代理以 DELETE 确认，以保证消息“at least once”送达；推送服务没收到确认时 SHOULD 继续重试到过期，也可以提前停止。“至少一次”是确认机制要达到的目标，不是协议保证；重复则是协议允许的结果。

RFC 8030 给了两件与重复有关的工具，适用范围都有限。第 5.2 节的 TTL 头是必填项，TTL 到期后推送服务“MUST NOT attempt to deliver”；服务可以缩短 TTL 并在响应里返回实际值，而且不负责计入应用服务器自己的发送耗时。第 5.4 节的 Topic 只替换“outstanding”的消息，即仍存储在服务里、尚未投递的那一份；已经推到设备上的消息不会被撤回。所以在超时后带同一个 Topic 重发，只能在原消息还没投出时把它替换掉，原消息已投出时用户照样收到两份。RFC 8030 本身没有定义请求级幂等键，POST 每次都创建新的消息资源。

邮件协议对同一问题写得更直接。RFC 5321 第 4.2.5 节规定，服务器在 DATA 结束后返回 2yz 就承担了投递责任；返回 4yz 或 5yz 则服务器不得再投递，责任仍在客户端。第 4.5.3.2.6 节解释 DATA 结束后等待 250 的超时为什么要设到 10 分钟：此时的伪超时“would typically result in delivery of multiple copies of the message”，因为服务器已经接受了。第 6.1 节从服务器一侧再提一次：为了避免超时造成重复，服务器必须尽量缩短对结束符的响应时间，并引用 RFC 1047 讨论这个问题（RFC 1047 本篇只取书目信息）。这两条把“接受之后、确认之前”的窗口标成了重复的来源，同时说明拒绝发生在接受之前时，重试是安全的。

HTTP 的通用规则在 RFC 9110 第 9.2.2 节：客户端不应自动重试非幂等方法，除非有办法知道请求语义实际上幂等，或者有办法检测原请求没有生效。前一种办法对应幂等键，Idempotency-Key 请求头目前只是 IETF 草案（draft-ietf-httpapi-idempotency-key-header-07，摘要描述其用途为让 POST、PATCH 容错）；后一种办法对应按业务引用查询。

接口与数据模型

服务接口只有两个入口：Notifier.create(user, eventKey, body, ttlSeconds, maxAttempts) 返回 (notificationId, created, tasks)；工作进程循环调用 Dispatcher.runOnce，每次完成一次“领取—调用—收尾”。人工出口是 Dispatcher.resolveManually(taskId, finalState, note)。

四张表分别承担不同的事实。

  • channel_pref(user_id, channel)：用户在每个渠道上的地址与开关，带版本号。
  • notification：逻辑通知，UNIQUE (user_id, event_key) 是逻辑去重的唯一依据，expires_at 是有效期。
  • delivery_task：每条逻辑通知在每个渠道上的任务，UNIQUE (notification_id, channel)；state 受 CHECK 约束限定在六个值内；attempt_token 标识当前持有的那一次尝试；outcome_uncertain 记录“上一次尝试可能已被接受”；needs_review 表示已停止自动调度、等待人工。另有 CHECK 要求 SENDING 状态必须同时带租约到期时间和令牌。
  • delivery_attempt：每次尝试一行，attempt_token 唯一，outcome 记录本次观察，late_outcome 记录被拒绝的迟到观察。

任务状态只描述“本服务对这次投递知道多少”，投递记录保留每一次观察的原文。结果未知时，任务表说“不确定”，记录表说“为什么不确定”。

拒绝路径有三条：领取查询找不到符合条件的行时返回空；收尾 UPDATE 的令牌或状态不匹配时影响 0 行，观察只写入 late_outcome；人工处理的 UPDATE 要求 state = 'UNKNOWN' AND needs_review，第二次调用影响 0 行。

正常路径与领取

创建通知在一个事务里完成：

插入成功的事务紧接着按启用偏好写入任务；没有拿到 id 的事务用新语句读取已存在的行并直接返回，不写任务。并发时，后到的 INSERT 会在唯一索引上等待先到事务的结果（PostgreSQL 16 INSERT 参考页说明带唯一索引的插入可能被并发会话阻塞；13.2.1 节说明 Read Committed 下 DO NOTHING 可能因另一事务的结果而不插入，即使该结果对本语句快照不可见）。随后的 SELECT 是一条新语句，在 Read Committed 下能看到已提交的那一行。这条保证的成立条件是唯一约束存在且事务级别为 Read Committed，观察位置是 N1 中 notification 行数与 created=true 的调用数，失败边界是有人绕过 create 直接写任务表，或者把 event_key 设计成每次请求都不同。

领取查询是整个调度正确性的第一处检查：

SKIP LOCKED 让并发领取者跳过已被锁住的行（PostgreSQL 16 SELECT 参考页的 Locking Clause 一节说明它提供不一致视图，适合多个消费者访问队列式表）；WHERE 中的状态与时间条件保证领取到的行确实可执行。偏好开关和有效期在同一事务里读取，因此“领取前关闭偏好”在领取时生效。失败边界：偏好只在领取事务里读一次，channel_pref 行没有加锁，领取提交到发出请求之间关闭偏好，本次仍会发送。领取成功后，同一事务把任务改成 SENDING、写入新令牌与租约、插入一条投递记录，然后提交，提交之后才发 HTTP 请求。HTTP 调用不在数据库事务内，这样慢渠道不会长时间持有行锁；代价是调用期间的保护只剩租约和令牌。

“查询后再决定”还有一个容易忽略的前提。替身在响应之前同步记录接受，所以超时后的查询一定能看到已接受的那一份。真实渠道的查询可能有延迟，原请求也可能仍在途中，此时“查不到”不能推出“没接受”。在没有这一承诺的渠道上，QUERY_NOT_FOUND 应该等原请求的最长处理时间过后再查，或者直接按结果未知停放。

关键实现

动作选择只看两个事实：上一次尝试是否可能已被接受，渠道是否支持幂等键。

uncertain 来自任务表的 outcome_uncertain，或者来自本次领取发现租约过期（上一个持有者失联，它的调用可能已被接受）。幂等渠道在不确定时仍然 SEND，因为幂等键 "ntf-" + ref 与任务绑定，跨尝试不变。

第二处检查在收尾。观察结果映射成新状态后，只有令牌仍是当前令牌时才写入：

影响 0 行说明这次尝试已被新的领取取代，代码只把观察写入该尝试的 late_outcome 并返回 STALE。超时、IO 错误、查询失败映射为 UNKNOWN 且 outcome_uncertain=true；预算用尽时 park 为真，next_attempt_at 置空、needs_review 置真，领取查询从此不会再选中它。

“未发送”的终态只能写给确定没有被接受过的任务。领取时发现偏好关闭或通知过期，如果此前有结果未知的尝试，就不能写 SUPPRESSED 或 FAILED，否则可能已外发的通知会被记成未发送；此时停放在 UNKNOWN：

B2 用例覆盖这个分支：sms 通知 TTL 2 秒，第一次调用在替身接受后超时，重试间隔 2500 毫秒，到下次领取时通知已过期。

替身确实外发过 1 次，任务表没有把它说成 FAILED。

同样的规则也适用于收尾。接受前的 503 或 400 只说明“这一次”没有被接受，证明不了之前那次超时的请求没被接受。finish 读取领取时写入的不确定标记，有未知前史时，503/400 保留标记，预算用尽或遇到 400 就停放：

进程死亡不会把任务改回 PENDING，任务停在 SENDING 直到租约（3000 ms）过期。新进程 w-p1-b 领取时把第一次尝试的记录补成 LEASE_EXPIRED，并把本次视为结果未知；push 渠道支持幂等键，于是带同一键重发，得到原消息号。若这是 sms 任务，同一位置的动作会是 QUERY。租约时长需要大于客户端超时加收尾耗时，否则持有者还在正常等待时任务就会被别人领走，下面的 P2 故意制造这种重叠。P1 中 w-p1-a 的租约 3000 ms 小于它的客户端超时 30000 ms，同样存在重叠，只因持有者已被杀才没有表现出来。

恢复流程

结果未知后的恢复按以下顺序执行，每一步都对应表里的一个可查询条件。

  1. 进程崩溃或暂停：不需要额外的恢复脚本。租约过期后，领取查询中的 state = 'SENDING' AND lease_until < now() 会选中该任务，领取事务把未结束的尝试记为 LEASE_EXPIRED，并把本次尝试标为结果未知。
  2. 结果未知且预算未尽：按渠道能力选择 SEND（同一幂等键）或 QUERY，每次都是新令牌、新记录。
  3. 预算用尽，或在未知状态下遇到偏好关闭、通知过期：停放在 UNKNOWN，needs_review = true，next_attempt_at 为空。
  4. 人工核对：操作员到渠道侧确认后调用 resolveManually，写入 SENT 或 FAILED 并追加一条 MANUAL_* 记录。T3 中第二次人工处理返回 0，说明重复调用不会把同一任务改两次。并发时依赖 Read Committed 下 UPDATE 等锁后重新求值 WHERE（13.2.1 节），本实验只测了串行重复调用。

恢复不会撤回已经送达的消息。如果渠道两次都接受了，本服务能做的是在记录里留下两次接受的证据，供下游去重或补偿。

F1 503 与 400；B1 偏好关闭与过期；B2 未知后过期；B3 未知后 503 真实组件 + 替身 PASS（B3 在修正前的代码上 FAIL）
P1 SIGKILL；P2 SIGSTOP/SIGCONT 多进程集成 PASS
NC3 只按 id 收尾（负向） 真实组件 暴露 SENT 被改回 UNKNOWN

这些结果只证明本地替身契约下的行为。替身没有实现 RFC 8030 的 TTL 头、Topic、投递回执，也没有到设备的链路；它的“503 在接受之前”和“查询立即可见”是人为设定的承诺，真实渠道需要逐项核对文档。幂等键存放在替身进程内存中，不涉及渠道侧的键保留期。所有进程共用同一数据库时钟判断租约，不覆盖时钟漂移、网络分区和数据库切换。C1 中各线程的尝试数分布（数值见 output.txt 的 note 行）每次运行都会变化，不作为公平性结论。完整限制见 evidence/33/LIMITS.md。
