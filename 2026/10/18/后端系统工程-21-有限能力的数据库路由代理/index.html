后端系统工程 21：有限能力的数据库路由代理

Created2026-10-18|Updated2026-10-23|系统架构
|Word Count:6.5k|Reading Time:23mins|Post Views:

系列导航：上一篇 20 发号服务的唯一性与失败模式 ｜ 本篇 21 ｜ 下一篇 22 非分片键查询与全局分页

账户表拆到两个 PostgreSQL 实例之后，每一次读写都要先回答“这一行在哪个库”。把这个问题从业务代码里拿走的常见做法，是在应用与数据库之间放一个路由层。路由层一旦被叫作“数据库代理”，读者往往默认它像一个数据库：任何 SQL 都能发，事务照常工作，会话参数照常生效。这种默认是错的。路由代理能承诺的范围，取决于它真正解析了什么、钉住了什么、拒绝了什么。

本篇实现一个能力有限的路由代理，并把限制写成接口的一部分：有限路由代理不等于兼容任意 SQL 或数据库协议。它只认一张分片表上的严格语法子集，只支持单分片事务，对子集之外的请求返回带编码的拒绝。代码在 examples/21-routing-proxy/，全部输出在 evidence/21/output.txt，证据边界见 evidence/21/LIMITS.md。

范围与不变量

业务对象是合成的测试账户：account(account_id, owner, balance, version)，account_id 是分片键。客户端需要的操作只有五类：按账户号读、按账户号改、按账户号删、插入一个新账户、在同一个分片内做多语句事务（例如两个账户之间转账）。

代理对客户端承诺下面几条，也只承诺这几条：

  • 每个账户号在任一路由版本下只映射到一个分片，插入和后续读写都去那个分片。
  • 一个显式事务内的全部语句在同一个后端连接上执行；事务一旦需要第二个分片，代理拒绝并让事务进入失败状态，绝不把一半语句提交到别处。
  • 子集外的语句不会到达后端。代理把解析结果重新生成为 SQL 再发出，客户端原文不直达数据库。
  • 某个分片不可用时，只有路由到它的请求失败，其它分片照常服务。
  • 路由表变化时，进行中的事务不更换目标。

规模取值全部是教学假设：两个分片，16 个桶，偶数桶在 s0、奇数桶在 s1；每个代理对每个分片最多 4 条后端连接；代理每 200ms 检查一次路由版本。实验没有测量吞吐和延迟，正文不给性能数字。

为什么不实现 PostgreSQL 线协议

让 psql 或 JDBC 直接连接代理，看起来最省事，代价是代理必须完整地扮演一个 PostgreSQL 服务器。按 PostgreSQL 16 前后端协议，至少要处理这些部分：

启动阶段的 StartupMessage 携带用户、数据库和任意会话参数，之后是认证往返，启动参数会成为会话默认值。Simple Query 的一个 Query 消息可以包含多条以分号分隔的语句，默认作为一个隐式事务执行，结束时回一个 ReadyForQuery。Extended Query 把一次执行拆成 Parse、Bind、Execute、Sync：命名的 prepared statement 存活到会话结束，命名的 portal 存活到当前事务结束，出错后后端丢弃消息直到 Sync。服务端在会话参数变化时主动发送 ParameterStatus。每个 ReadyForQuery 带一个事务状态字节，消息格式对它的定义是：“‘I’ if idle (not in a transaction block); ‘T’ if in a transaction block; or ‘E’ if in a failed transaction block (queries will be rejected until block is ended)”。

这些状态都长在后端会话上。代理一旦为了节省连接把多个客户端复用到同一批后端连接，就要逐项决定：A 准备过的语句在 B 借到的连接上不存在时怎么办，A 改过 DateStyle 后要不要在换连接时重放，一个 Query 消息里三条语句分属两个分片时怎么办。PgBouncer 的做法提供了一份现成的边界清单：它的 features 页说明 transaction pooling “breaks client expectations of the server by design”，并在特性表里把 SET/RESET、LISTEN、WITH HOLD CURSOR、PREPARE / DEALLOCATE、LOAD、会话级 advisory lock 标为 transaction 模式下 “Never”；协议级 prepared statement 要到 1.21.0 才通过 max_prepared_statements 跟踪支持（changelog）。PgBouncer 的定位是连接池，不负责分片路由，仅连接复用一项就需要这样一张表。

解析器（src/SqlParser.java）的检查顺序决定了错误码是否准确。先做一遍识别字符串边界的扫描，找注释和分号，因为它们在分词之前就能改变语句的含义；再看首个关键字，把 DDL 和会话状态语句挑出来，这样 SET statement_timeout = '1s' 得到 R25，而不是因为含有字面量得到 R28；然后分词并拒绝一切字面量、引号标识符、JOIN、多余的 SELECT；最后才按语法逐词匹配。WHERE 子句只有两种形状：

WHERE balance = ? AND account_id = ? 在语义上同样钉住了分片键，仍被拒绝。允许任意顺序的合取条件，就要写一个能判断“这组条件是否把分片键限定为有限个值”的分析器，OR、NOT、函数调用都会进入这个问题。严格顺序把这类判断从代理里移走，代价是客户端必须按固定形状写 SQL。

参数绑定按列类型进行：account_id 传 abc 得到 R27，不会被拼进 SQL。代理发给后端的是自己生成的语句，例如 update account set balance = balance - ? where account_id = ?，所以拒绝规则同时是一道注入边界。

路由与路由表

路由函数是 bucket = floorMod(splitmix64(account_id), 16)，再查 route_bucket[bucket] 得到分片（src/RouteTable.java）。桶数固定、桶到分片的映射可变，这样移动数据时只需改映射，不需改哈希函数。Vitess 用 Primary Vindex 表达同一件事：它把列值映射为 keyspace ID，插入时由这个映射决定目标分片，官方文档称其“conceptually … equivalent to a NoSQL Sharding Key”（Vitess v24.0 Vindexes）。本章的桶就是一个极简的 keyspace ID。

代理在一个可重复读的只读事务中读取三张元数据表，保证版本号和映射来自同一快照。新表必须满足两个条件才会替换旧表：版本号严格递增；每个桶恰好有一行且指向已知分片。否则记录被拒版本并保留旧表。invalid_route_table_rejected 先写入缺少桶 15 的版本 4，再写入版本号回退到 3 的表：

连接绑定与事务状态

自动提交语句按当前路由表选分片，从该分片的池里借一条连接，执行后归还。显式事务不同：BEGIN 只记录当前路由表快照，不占用后端连接；第一条数据语句按快照路由，借出连接、关闭自动提交并钉在会话上，直到 COMMIT 或 ROLLBACK 才归还。

图 21-2：会话事务状态机（前置条件与拒绝路径）

stateDiagram-v2
  [*] --> I
  I --> I: 自动提交语句（借连接→执行→归还）
  I --> T0: BEGIN / 记录路由快照 rv
  T0 --> T1: 首条数据语句 / 按快照路由，借连接并钉住
  T0 --> I: COMMIT 或 ROLLBACK（无后端往返）
  T1 --> T1: 同分片语句（同一 pid）
  T1 --> E: 路由到其它分片 R12 / 后端错误 R31 / 子集外语句<br/>代理立即回滚并归还连接
  T0 --> E: 子集外语句 / 分片不可用 R30
  T1 --> I: COMMIT 成功 / ROLLBACK
  E --> E: 数据语句与 COMMIT 返回 R13；其它请求返回各自拒绝码
  E --> I: ROLLBACK
  T1 --> T1: BEGIN → R40，状态不变

T0 与 T1 对客户端都显示为 T，区别只在是否已经钉住连接。进入 E 的那一刻，代理就在后端执行回滚并把连接还给池，后端事务已经结束，会话只是在等客户端确认。代理还加了一条自己的规则：E 状态下的 COMMIT 返回 R13。PostgreSQL 16 的 COMMIT 文档没有说明失败事务块中执行 COMMIT 会怎样。代理不模仿这一未写明的行为，要求客户端显式写出 ROLLBACK，误以为可以提交的客户端因此一定收到错误。

需要跨分片原子性时，有三条路径：

方案 代理需要承担的 失败时留下什么 本章取舍
拒绝跨分片事务（本章） 绑定检查与 R12 无部分提交；业务需要把同一事务的数据放在同一分片，或改用下两种方案 采用

两阶段提交在 PostgreSQL 上有现成的原语，但原语本身说明了它的成本。PREPARE TRANSACTION 执行后“the transaction is no longer associated with the current session”，它“is not intended for use in applications or interactive sessions”，目的是让外部事务管理器做跨库原子提交；准备好的事务“continues to hold whatever locks it held”，文档建议在没有事务管理器跟踪时把 max_prepared_transactions 保持为 0，而它的默认值正是 0（资源配置）。把这些放进代理，代理就要有自己的持久日志、恢复流程和超时决断，它从一个可以随时 kill -9 的无状态进程变成需要备份和高可用的协调者。Vitess 的 TwoPC 模式也要求在 tablet 上配置判定事务被遗弃的时长，并且文档说明它不提供跨分片隔离，跨分片查询可能看到正在提交中的部分结果。本章的验收目标是“不误切、显式拒绝”，两阶段提交超出这一目标。

客户端路由库还是独立代理

同样的路由逻辑可以做成应用内的库：

维度 客户端路由库 独立代理进程
网络跳数 应用直连分片 多一跳
连接数 每个应用实例 × 每个分片各一个池，随实例数增长 由代理实例数决定，可以集中限额
路由表一致性 每个实例各自加载，升级要覆盖所有语言与版本 代理实例少，版本集中
故障面 与应用同生共死 新增一个必须高可用的组件；代理崩溃时其上全部事务回滚
拒绝规则 可以在编译期或调用前检查 运行时按协议返回错误码

两者的绑定、拒绝和路由版本规则相同，差别在部署与运维。本章选独立进程，是为了能用 kill -9 检验“代理崩溃不留部分提交”，以及让 naive 与 strict 两种实现在同一组分片上并排运行。

代理进程被 kill -9：测试先经新代理提交一笔 50 的转账，再开启一笔 100 的转账并停在两条 UPDATE 之后，然后杀掉代理。内核关闭了代理的套接字，PostgreSQL 读到连接结束，回滚并退出该后端：

已提交的 50 保留，未提交的 100 没有出现。这里的回滚由 PostgreSQL 完成，与代理代码无关；代理能保证的是一个事务只在一个连接上，所以“连接断开即回滚”覆盖了整个事务。同一实验若换成 naive 代理，被拆到自动提交连接上的那一半在崩溃前已经提交。

事务内三条语句都在 s0、rv=1、同一 pid 上执行，提交后 s0 余额加 2；提交之后的查询和新事务都按 rv=2 去了 s1，在那里查不到这一行，因为实验只改了映射，没有搬数据。这条结果同时暴露了本章路由版本的边界：如果桶在某个事务 BEGIN 之后被迁走，这个事务仍会写旧分片。阻止这类迟到写入需要在分片端检查路由版本或设置写栅栏，这是第 23 章的内容。

结论边界

这些实验支持的结论限于本章定义的子集：在两个真实 PostgreSQL 分片上，代理按版本化的桶映射路由单键语句；一个显式事务只使用一个后端连接，跨分片时显式拒绝而不是部分执行；子集外语句与会话状态语句在入口被拒，不会污染池化连接；客户端断开、代理被 kill -9、单个分片停止时都没有留下部分提交，故障范围限于对应会话或分片。

它们不支持以下说法：代理兼容 PostgreSQL 协议或任意 SQL（没有实现线协议，只认上文的语法）；跨分片事务可以原子提交（本章拒绝它们）；路由表切换时数据保持一致（实验只改映射，切换后新分片上查不到行）；跨机器故障下后端会及时回滚（本地 kill -9 由内核立刻关闭套接字，掉电或网络分区要依赖 TCP keepalive 或 idle_in_transaction_session_timeout，未测试）。吞吐和延迟没有测量。

这个代理拒绝了所有不带分片键的查询。按 owner 查账户、跨分片分页列出账户，是下一篇 22 非分片键查询与全局分页 要解决的问题；路由表变化时怎样搬数据、怎样拦住迟到写入，留给第 23 章。
