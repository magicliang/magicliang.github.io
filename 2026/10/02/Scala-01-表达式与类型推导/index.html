金额计算为什么会突然变成 Unit

一个函数先计算金额，再打印日志。如果最后一行从 subtotal + shipping 换成 println(subtotal + shipping)，代码并没有停止执行，但返回结果已经改变。Scala 的代码块可以产生值，尾表达式参与确定整个块的结果。日志会输出金额，却不会因此成为那个金额。

这一点把语法、求值与类型联系起来。表达式的静态类型说明它允许怎样使用；运行时值是某次执行的结果；副作用是执行中对外部状态的改变。三个维度不能互相替代。看见日志打印 28.20，不足以证明函数返回 BigDecimal，也不能说明一个分支不会抛异常。

本章在 Scala 3.3.7 下，从订单金额的小例子推导代码块、分支和底类型，再检查类型推导何时保留联合、何时选择公共父类型。类型关系完整展开在后续章节，本章只使用解释这些结果所必需的部分。

Unit 有值，Nothing 没有正常结果

Unit 的值写作 ()。它适合表示“调用已完成，但结果不携带额外信息”。println 和许多修改状态的方法返回 Unit，调用者可以观察它们的副作用，却不能把这个返回值当作打印出来的数据。Scala 3 类型入门给出了这一类型层次的基础定义。

因此“返回 Unit”不等于“完全没有值”。在 Scala 语义中可以把 () 绑定到变量；它的结果信息量很少，但仍是值。也不应从这个语言事实反向推断 JVM 对任何 Unit 表达式都必须分配一个对象，编译目标与使用位置可能采用不同表示。

正常分支产生 BigDecimal，另一个分支中断正常返回。后者不会要求调用者拿到一个“异常类型的金额”，因为异常传播与函数的正常结果是两条控制流。这解释了函数为何仍可声明返回 BigDecimal。

不能把 Nothing 解释为 null。默认 null 相关规则处理的是可能出现的空引用；Nothing 是没有正常值的类型。也不能说“所有永不结束的代码都推导为 Nothing”：一个语法上的 while 循环可以有 Unit 类型，即使程序员让它无限执行。类型检查根据语言规则和表达式形式推导，不是自动完成终止性证明。

println(subtotal) Unit 值 () 输出文本
throw exception 不正常返回值 异常向调用者传播
if ... then ... else ... 被选分支的结果 取决于该分支是否有副作用

Scala 3.3.7 也不能套用“一旦分支不同就推导为 Any”的口令。冻结版的透明父类型说明解释了联合类型在只有透明公共父类型时可以被保留。于是该例没有显式标注 mixed，仍可以通过后续联合类型赋值检查。

但这个结果不是“任何不同子类都会保留精确联合”。如果两个类实现普通公共父类型，推导可能选择那个父类型，隐藏分支各自的精确信息。

反例建立一个普通 Status 父类型：

第一行局部绑定允许推导选择 Status；第二行又要求精确到 Created 或 Paid。Status 接口本身并未禁止其他实现，所以仅凭一个静态类型为 Status 的值，不能无条件满足更窄的联合。此处检查的不是运行时对象到底是哪一个，而是绑定后仍保留多少静态信息。

修复有两条含义不同的路径。若 API 真正需要限制为两个实现，直接为 state 标注联合类型；若 API 只需要 Status 承诺的操作，保留公共接口并调整调用者，不强制要求更窄的结果。选择取决于边界上需要表达的契约，不能把更多类型细节一律视为更好的设计。

透明父类型的对照实验则定义 transparent trait Token，两个子类分别为 OrderToken 与 ProductToken。它们的条件表达式可以保留联合，然后赋值给显式的 OrderToken | ProductToken。源码和断言在 Chapter01.scala，检查只用于验证本版的推导差异，不是建议把所有公共接口都改成 transparent。

这些规则会随着语言版本和上下文约束变化。文章采用固定版本文档与编译正反例交叉核对，不能只从当前 REPL 的一行显示推广到全部 Scala 3。后续类型系统篇会讨论更多推导边界，本章保留最小反例即可。

显式返回类型是一条外部契约

自动推导减少了重复标注，但它不能替 API 设计者决定应向调用者暴露什么。一个公开方法只依赖最后表达式推导时，内部加入日志、调整分支或改变返回对象，就可能同时改变公开类型。显式返回类型让这些修改必须继续满足原契约。

例如金额函数声明返回 BigDecimal，最后误改成 println 时会在编译阶段暴露；若无标注，代码可能推导为 Unit，问题直到调用者想做金额计算才出现。推导本身没有错误，是程序没有在需要稳定契约的边界写下约束。

局部中间结果可以保持简洁，公开边界则应根据可读性和演进要求决定标注。每个变量都重复写类型并不会自动提高安全性，也可能压住推导想表达的关系。可迁移的判断是先确定契约边界，再看哪项信息需要稳定，而不是在“全部标注”和“全部省略”之间选阵营。

运算符也参与表达式结构

本章保留两项简单断言：2 + 3 * 4 得到 14，(2 + 3) * 4 得到 20。先决定解析形成的表达式结构，再按结构求值，不能用日志的先后输出猜测优先级。Scala 的中缀写法还可以调用方法，看到符号样式并不意味着它是独立于对象方法的特殊运算系统。

对于业务代码，括号可以明确关键分组，避免读者必须记住所有符号优先级。自定义运算符、右结合与重载的完整规则不是本章主题；它们需要在解释实际 DSL 时逐项验证。这里不把“看上去像数学公式”当作可读性的充分条件。

练习与答案

另一项控制流检查是 fee(0)：它应抛出 IllegalArgumentException，不能拿到金额零。若业务约定零数量代表无需收费，应明确改变正常分支和返回规则，再增加该输入的断言。Nothing 能使异常分支与正常返回类型协作，却没有判断“零数量应该免费还是非法”。这项决定仍属于领域契约。

手算：将金额块最后一行写成 val finalAmount = subtotal + shipping，没有再补 finalAmount，块还能作为金额返回吗？答案是否定的，最后是定义语句，没有把所定义的金额作为块结果交出。补一行 finalAmount 可恢复所需结果；若外层已经标注返回类型，编译器会帮助发现遗漏。

改动练习：把普通 Status 示例中的 state 显式标为 Created | Paid，保持两个分支不变，再尝试赋给 Status。前一步保留精确联合，后一步仍符合公共父类型约束。两种赋值方向不同：窄信息可以用于更宽接口，已经拓宽的静态类型不能无条件倒推为窄联合。
