深入 Hibernate 01：同一数据库行对应几个 Java 对象

Created2026-10-04|Updated2026-10-10|技术
|Word Count:2.1k|Reading Time:7mins|Post Views:

实验材料状态：下文保留先前 PostgreSQL 16.15 的原始记录。当前检出版本在专用 PostgreSQL 16.15 上复跑 00–03，6 项测试通过；新运行的报告在 examples/hibernate-lab/evidence/00-03/20261003T030855Z-pg16-cumulative/。主仓另保留 2026-10-02 的 PostgreSQL 17.6 原始运行；2026-10-03 同步后在 PostgreSQL 17.6 复跑 00–12，50 项通过，见 examples/hibernate-lab/evidence/00-12/20261003-pg17-synced-local/。两种环境的运行分别留证。

一行不是一个全局 Java 对象

订单服务按数据库主键查询 PurchaseOrder 两次，两次返回值是否满足 ==？只有在说明查询发生在哪个持久化上下文、上下文是否被清空之后，这个问题才有答案。同一张订单在不同请求中也可能同时以两个 Java 对象表示，不能据此推断数据库有两行，或从 Java 引用相同推断另一个事务的可见性。

业务模型沿用第 00 篇的单表订单：id 是数据库标识，order_no 是业务编号，request_key 是幂等键。这里的工作单元仅表示一个 Session 内跟踪的实体集合与变更，不等同于“某次方法调用”“一条物理连接”或者“数据库的一次提交”。本篇没有增加关联实体，更没有用单表测试宣称抓取对象图的成本已经得到验证。

对象身份的作用域是上下文

PurchaseOrder 没有重写 equals()。因此 == 只判断两个 Java 引用是否指向同一实例；数值相等的 id 则判断它们是否映射到同一张订单。独立的 Session 各有自己的持久化上下文，即使在同一个 SessionFactory 中，仍可分别装载代表同一行的不同实例。clear() 解除当前上下文的托管关系，不删除数据库行，也不会把旧对象所有字段抹掉。

冻结源码中，EntityKey 的构造拒绝空标识符；哈希及比较使用实体根类型和标识符的类型契约，而不是调用任意业务对象的 equals()。StatefulPersistenceContext.addEntityHolder() 以 EntityKey 为键存放实体 holder：如果键已存在，则保留已有 holder 并把实体放进去；否则放入新 holder。getEntity(EntityKey) 在没有 holder 或 holder 仍未初始化时返回 null，否则返回已加载实体。这一分支说明“键存在”仍需要检查初始化状态，不能把所有代理行为概括成普通 Map.get()。

入口 SessionImpl.get(Class, Object) 委派给 byId(...).load(...)，不是每次显式 new 出对象后无条件发 SQL。持久化上下文只保证本上下文已托管实例的一致引用；不承担第二级缓存的跨 Session 复用，更不修改数据库隔离级别。对应上游 MultiLoadTest.testDuplicatedRequestedIds() 对同一上下文请求重复 id 时用 assertSame 验证实例身份，但它的入口是 multiLoad，不代替本篇的两 Session 与 clear 实验。

从状态角度看，第一次 get 可能经 JDBC 装载实体并把它纳入本上下文；第二次相同标识的 get 可以复用托管实例。另一 Session 的上下文没有这个条目，需要独立读取或从其他缓存机制获取数据，得到的 Java 引用不共享。清空第一个上下文后，原对象变为脱管对象，下一次加载得到新的托管实例。这里的“需要读取”不是保证必定执行一次 JDBC 查询：二级缓存、锁模式和获取策略可能改变实际 SQL；本章没有打开二级缓存，实际日志另列。

join 行数为什么不能用对象数代替

当一个查询要返回父订单及子行时，即使同一个 Session 里订单对象只有一份，关系结果集也未必只有一行。先不引入 OrderLine 映射，手算以下未来模型的内连接：订单 A 有行 1、行 2，订单 B 有行 3。orders JOIN lines ON ... 产生 (A,1)、(A,2)、(B,3) 三行，结果中的不同订单 id 只有 两个。订单 C 没有行，内连接不出现；换成左连接才可能多出 (C,NULL)。这只是关系运算的手算，不是本章已执行过集合抓取分页实验。持久化上下文维护 Java 对象身份，不会替数据库减少 join 的中间行数或网络传输量。

手算题。 同一个 Session 内对 A 执行两次 get，在 B Session 再执行一次 get；随后 A Session 调用 clear() 并再次查询。若记录了这四个引用，最多有几个不同的 Java 实例、对应几个数据库主键？答案是三个实例、一个主键：A 的前两次同一引用，B 的一次独立，A 清空后再次加载得到第三个实例。本章不从这一答案推算 JDBC 查询次数。

改动练习。 注释掉 firstSession.clear()，并将紧随其后的 assertFalse(firstSession.contains(first)) 改为 assertTrue(firstSession.contains(first))，补上 import static org.junit.jupiter.api.Assertions.assertTrue;，保留 assertNotSame(first, afterClear)。预期失败于 assertNotSame，因为 first 仍是同一个 Session 托管的已加载实例；若只注释 clear()，测试会先在 assertFalse 处失败。恢复 clear() 和 assertFalse 后，预期断言通过。这项修改只改变上下文内部身份，并不对数据库行执行删除或更新。若想验证后者，需要另起连接读取或检查 SQL/DML，而不能从 contains() 推断。
