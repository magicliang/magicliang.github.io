Python 00：从哪个 Python 开始复现

Created2026-10-07|Updated2026-10-22|Python 语言与工程
|Word Count:2.1k|Reading Time:7mins|Post Views:

一段词频脚本在终端运行成功，换一个终端却提示 No module named tasklab。代码没有变，执行它的命令、工作目录和模块搜索路径可能已经变了。还没讨论对象或并发，实验的第一条输入就应当是“由哪个解释器、在什么条件下运行”，而不是仅仅保存一段源码。

本系列使用一个累计扩展的任务应用 tasklab：提交人工生成的文本、执行白名单词频任务、查询状态、请求取消。00 只做进程内顺序执行。数据库、安装包与服务接口在后续章节加入，不能用此处的一次运行推断它们已经可用。

这里的 demo 暂时是可复现的实验入口，不是正式 CLI。未来多次 CLI 调用要共享任务，必须等 21 引入持久化；现阶段每次启动都是新的进程内存。

固定哪一层版本

以下 Ubuntu 版本和逐章测试数量是 2026-10-07 留存的历史实验。本仓库另在 2026-10-12 用 macOS arm64 的 CPython 3.12.3 复跑当前累计源码、重新构建并安装 wheel；完整版本、二进制哈希、编译参数和 SQLite 版本见 examples/python-language/evidence/completion/acceptance/cpython-environment.stdout。相同补丁号不能把两个平台视作同一个构建；复现命令应以 RUN.md 的可选解释器路径为准，不能要求 macOS 上存在 /usr/bin/python3.12。下文上游 tag 是参考源码定位，不能单凭它推定新二进制的全部下游补丁。

sys.version 的实测值是 3.12.3 (main, Aug 31 2026, 10:18:26) [GCC 13.3.0]，解释器路径是 /usr/bin/python3.12，系统包版本为 python3.12-minimal 3.12.3-1ubuntu0.17，平台为 Ubuntu 24.04.4 LTS、x86_64。编译选项包括 --enable-shared 和 --without-ensurepip，链接的 SQLite 为 3.45.1。二进制 SHA-256 和完整配置记录在仓库的 examples/python-language/evidence/00/20261007-baseline/environment.txt。

版本号相同仍不等于二进制完全相同。本机安装的是带发行版补丁的 CPython：上游源码 tag 为 v3.12.3，对应 commit f6650f9ad73359051f3e558c2431a109bc016664；本机包还对应 Ubuntu 3.12.3-1ubuntu0.17 的 .dsc、原始源码包和补丁包。两份源码包已下载，并按 .dsc 内的 SHA-256 校验。只把上游 commit 写作“本机的精确源码”会漏掉发行版补丁。相关网址、校验值和未执行的签名验证均在环境记录中。

资料依据 Python 3.12 文档分支。它提供该版本的接口描述，不代表文档网页的日期就是本机二进制的构建时间，更不代表正文已在 Python 3.14 或其他构建上验证。构建、实际 GIL 状态也要分开说：这台机器是通常的 CPython 3.12 构建，Py_GIL_DISABLED 未启用，探测时当前线程持有 GIL；此版本没有 sys._is_gil_enabled 接口。本记录没有 free-threaded 构建，也没有扩展兼容性实验，不能由它推测 38 的结果。

还有三份不同的依赖事实：pyproject.toml 的直接运行依赖声明是空列表；构建工具、解析锁与静态检查器尚未选择；当前运行使用的是系统已安装的解释器与标准库，不是从 wheel 干净安装得到的环境。声明、解析结果、实际安装三者不能互相替代。

预测题

保持工作目录和解释器不变，去掉 PYTHONPATH=src 后再执行 python -m tasklab.demo，会怎样？改变解释器的版本号但保留环境变量，能否推出词频输出一定变化？

答案：在当前未安装 tasklab 的环境中，解释器不能从默认搜索路径找到源码包，模块查找在任务函数之前失败；实际输出还取决于环境中是否另外安装了同名包，所以预测前须检查安装状态。版本号变化也不足以单独推出业务输出变化；要固定输入并重新执行，记录新解释器的路径、依赖和断言结果。这里没有把未执行的跨版本对照算成通过。

变更题

把拒绝场景的任务类型改为合法的 word_count，同时把文本改成 None。需要检查什么，才能断定非法提交没有污染已有任务？

答案：期待 TypeError；对比拒绝前后的旧任务快照及 len(store["tasks"])，再提交一个合法任务检查 ID 是否仍为 task-0002。仅检查退出码不能证明旧状态没变；仅检查错误文本也不能证明编号没被消耗。这组断言已由本章 test_invalid_input_preserves_existing_tasks_and_id 执行。
